# ADR-001: 게임플레이 아키텍처와 설계 패턴 선택

> 상태: 검토 중
> 날짜: 2026-11-28
> 결정자: 사용자 검토 필요
> 관련 GDD/계획: [GDD](../design/001_2026-11-28_tower-defense-gdd.md),
> [구현 로드맵](../planning/M0-implementation-roadmap.md)
> 대체 문서: 없음

## 맥락

현재 프로토타입은 씬, 맵, 적, 타워, 웨이브, 경제의 기본 모듈을 갖고 있으나
`gameplayScene`이 입력 해석, 상태 전이, 배치, 전투 결과 적용, 스폰 연결,
재경로 지정을 함께 조정한다. 또한 `GameMap`, `Tower`, `Enemy`가 데이터와 그리기
행동을 함께 가지며, `Hud`가 전체 씬을 인자로 받아 상태를 직접 읽는다.

앞으로 실시간 편집, 원자적 판매·환급, 레벨별 웨이브, 업그레이드, 다음 위협
예고를 추가하면 현재 구조에서는 하나의 입력이 여러 객체를 부분적으로 갱신한
뒤 실패할 가능성이 커진다. 기능 구현 전에 상태 소유권, 명령 경계, Model-View
계약을 결정해야 한다.

## 결정 동인

- 벽·타워 배치, 제거, 판매, 경로 재계산을 하나의 성공/실패 거래로 처리
- 고정 타임스텝에서 같은 입력이 같은 시뮬레이션 결과를 생성
- `love.*` 없이 Model과 상태 전이를 헤드리스로 검증
- 작은 Lua 모듈과 명시적 의존성 유지
- 입력·HUD·렌더링 변경이 핵심 전투 규칙을 흔들지 않도록 분리
- 교육 프로젝트에 적합하게 패턴 수를 최소화하고 책임을 읽기 쉽게 유지

## 검토한 선택안

### 선택안 A - 현재 Scene 중심 구조 유지

- 장점:
  - 지금 수정량이 가장 적다.
  - 처음 구현을 빠르게 이어갈 수 있다.
- 단점:
  - `gameplayScene`의 조정 책임과 상태 변경 책임이 계속 커진다.
  - 원자적 편집과 실패 롤백을 여러 호출자에서 반복하게 된다.
  - 렌더링 없는 통합 시뮬레이션이 어렵다.
- 위험:
  - UI 입력 하나를 추가할 때 전투, 경제, 맵 규칙을 함께 회귀할 수 있다.

### 선택안 B - 최소 MVC + Command + Data-driven Factory

`GameModel`은 게임 상태와 시뮬레이션을 소유하고, Controller는 입력 명령을
생성하며, View는 읽기 전용 스냅샷을 그린다. 배치·제거·판매·업그레이드는
원자적 Command로 처리한다. Wave, Enemy, Tower 정의는 정적 데이터에서 팩토리로
생성한다.

- 장점:
  - 상태 소유권과 실패 경계가 명확해진다.
  - `RT-01`~`RT-08`, `EC-01`~`EC-08`을 헤드리스 통합 하네스로 검증할 수 있다.
  - 현재 작은 씬 구조와 기능을 유지하면서 점진적으로 이동할 수 있다.
  - 패턴이 실제 문제인 거래, 상태 전이, 데이터 생성에만 적용된다.
- 단점:
  - 초기 파일과 어댑터 수가 증가한다.
  - DTO/스냅샷 경계를 과하게 만들면 코드가 무거워질 수 있다.
- 위험:
  - Model을 지나치게 세분화하면 교육 코드의 추적성이 떨어질 수 있다.

### 선택안 C - ECS 중심 재설계

- 장점:
  - 유닛 수가 매우 많아질 때 컴포넌트 배치와 시스템 병렬 확장에 유리하다.
- 단점:
  - 현재 적·타워 수와 기능보다 구조 비용이 크다.
  - Lua 교육 프로젝트와 원자적 편집 검증의 주요 문제를 직접 해결하지 않는다.
- 위험:
  - 기능 구현보다 ECS 기반 인프라가 주요 작업이 되어 방향 드리프트를 만든다.

## 선택 기준과 잠정 평가

아래 평가는 현재 요구와 코드 사실을 기준으로 한 비교 초안이다. 높은 점수는
적용 승인을 뜻하지 않으며, 사용자 검토용 판단 근거다.

| 기준 | A: Scene 중심 유지 | B: 최소 MVC + 거래 | C: ECS |
|---|---|---|---|
| 현재 코드와의 이동 비용 | 가장 작음 | 중간 | 가장 큼 |
| `RT-*` 원자적 편집 검증 | 낮음: Scene 여러 단계에 분산 | 높음: 거래 경계로 표현 | 중간: 시스템 경계 추가 필요 |
| `EC-*` 실패 시 불변 검증 | 낮음: 비용·맵·대상을 호출자가 직접 순서 제어 | 높음: 후보→확정 단일 계약 | 중간: 컴포넌트 간 다단계 시스템 필요 |
| 헤드리스 통합 테스트 | 낮음: Scene이 View/상태를 함께 보유 | 높음: Model을 단독 실행 가능 | 높음: 시스템 실행 가능 |
| 교육용 추적성 | 가장 높음 | 충분함: 파일이 늘지만 책임이 명확 | 낮음: 엔터티·컴포넌트·시스템 지식 필요 |
| 입력/UI 확장 | 중간: HUD·Scene 결합 증가 | 높음: 명령과 표시 계약 분리 | 높음: 별도 프레젠테이션 필요 |
| 현재 적/타워 규모의 필요성 | 충분함 | 충분함 | 과도할 가능성 |

### 선택 게이트

- **A를 선택할 수 있는 조건**: 실시간 편집을 Scene 외부 통합 객체로 분리하지
  않고도 `RT-*`, `EC-*`의 원자성을 한 곳에서 모두 검증할 수 있어야 한다.
- **B를 선택할 수 있는 조건**: Model/View 분리를 위해 추가될 파일 수보다
  통합 테스트와 실패 추적성이 실제로 개선되어야 한다.
- **C를 선택할 수 있는 조건**: 현재 객체 지향 루프에서 실제 성능 병목 또는
  매우 많은 동시 엔터티가 측정되어 ECS 전환 비용을 정당화해야 한다.

현 시점 자료만으로는 B가 가장 적합해 보이지만, `src/`를 변경하기 전
characterization harness와 사용자 검토를 통과해야 최종 승인을 결정한다.

## 제안 결정

선택안 B를 기본안으로 제안한다. 다만 한 번에 대규모 재작성하지 않고 아래
경계를 한 번에 하나씩 도입한다.

1. **Scene/Composition Root**: `main.lua`와 씬이 의존성을 조립한다.
2. **Controller**: 입력 스냅샷을 `Preview`, `Confirm`, `Cancel`, `StartWave`
   같은 명령으로 변환한다.
3. **GameModel**: 고정 스텝 상태 전이와 성공/실패 결과를 소유한다.
4. **Command/Transaction**: 편집·판매·업그레이드는 후보 계산 뒤 전체 확정하거나
   전체 거절한다.
5. **Domain Modules**: Map, Pathfinder, Economy, CombatRule, WaveRuntime은
   `love.*` 없이 동작한다.
6. **Factory + Data**: Enemy/Tower/Wave 인스턴스 생성은 정의 데이터와 분리한다.
7. **View**: 씬/HUD는 Model을 변경하지 않고 읽기 전용 표시 데이터만 사용한다.
8. **Scene State**: 기존 씬 스택과 build/wave/result 전이는 유지한다.

ECS, 전역 Event Bus, 서비스 로케이터는 첫 구현 범위에서 사용하지 않는다.

## 근거

- 최소 MVC는 현재 프로젝트 규칙과 기존 `01_core` 씬·고정 타임스텝 구조를
  유지하면서 상태 결합을 줄인다.
- Command/Transaction은 경로 편집과 판매의 원자성 요구를 직접 표현한다.
- Data-driven Factory는 레벨별 웨이브와 정의 분리를 요구하는 `TD-003`에 직접
  대응하면서 대규모 프레임워크를 만들지 않는다.
- ECS는 현재 규모와 학습 범위를 넘어 과도한 비용이 예상된다.

## 결과

### 긍정적 결과

- 실시간 입력 없이 핵심 게임 상태를 빠르게 시뮬레이션할 수 있다.
- 편집·경제 실패 시 Model 변경 위치가 제한된다.
- HUD, 다음 위협, 결과 화면이 게임 규칙을 직접 변경하지 않는다.
- 레벨 데이터와 실행 엔진의 변경 이유가 분리된다.

### 부정적/비용 결과

- 초기 전환에 모델 스냅샷, 명령 결과, 모듈 조립 코드가 필요하다.
- 프로토타입 메서드 일부는 임시 어댑터를 거쳐 점진적으로 옮겨야 한다.
- 직접 객체 접근에서 읽기 전용 View 계약으로 전환하는 기간에 하네스 수정이
  필요하다.

### 영향 파일 또는 경계

- 주요 영향: `src/03_game/scenes/`, `src/03_game/`, `src/04_ui/`, `tests/`
- 1차 영향 금지: 타워·적 밸런스 수치
- 별도 검토: 씬 스택, 고정 타임스텝, 가상 해상도는 이미 역할이 분리되어 있어
  변경을 시작점으로 삼지 않는다.

## 불변 조건

- 모든 상태 변경은 고정 타임스텝으로 수렴한다.
- `update`와 `draw` 책임은 분리한다.
- Model은 입력 장치, 렌더링, 파일 I/O, `love.*`에 의존하지 않는다.
- View는 Model을 수정하지 않는다.
- Lua 5.1/LuaJIT 문법과 명시적 지역 모듈을 사용한다.
- 기능 추가보다 먼저 기존 동작을 보호하는 하네스를 확보한다.

## 검증

| 확인 항목 | 방법 | 기대 결과 |
|---|---|---|
| Model 순수성 | 정적 의존성 확인과 `love` 없는 하네스 | Model 하위 트리에서 `love.*` 미사용 |
| 결정성 | 같은 fixed-step 입력 반복 시뮬레이션 | 위치·골드·스폰·결과가 동일 |
| 원자적 거래 | `RT-01`~`RT-08`, `EC-01`~`EC-08` 통합 테스트 | 실패 시 전체 상태 불변 |
| View 경계 | HUD/Renderer 정적 확인 | 입력 처리와 Model 변경 없음 |
| 런타임 제한 | 필요한 경우 세로 화면 전체 실행 1회 | 입력/HUD/프레임 확인 후 종료 |
