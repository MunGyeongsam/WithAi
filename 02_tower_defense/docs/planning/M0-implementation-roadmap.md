## 마일스톤 순서

### M1 - 경계와 characterization harness

- 목표: 현재 플레이 동작을 수정 없이 테스트 가능한 계약으로 보호한다.
- 주요 결과: Model 후보 경계, scene orchestration 기준선, 기본 웨이브/전투/경제
  하네스 통과.
- 종료 조건: 현 구현의 정상·실패 동작이 문서화되고 주요 회귀 하네스가 녹색이다.
- 선행 조건: ADR-001 구조 검토 승인.

### M2 - 경로 편집 원자성

- 목표: Command/Transaction을 사용해 배치·제거와 모든 적 합류를 원자적으로
  처리한다.
- 주요 결과: `RT-01`~`RT-08` 통합 하네스와 거절 상태 불변.
- 종료 조건: 실패가 골드·맵·경로·적 상태를 바꾸지 않는다.
- 전체 실행: 입력 미리보기와 시각적 합류가 필요할 때만 최소 실행.

### M3 - 경제·판매·업그레이드 거래

- 목표: 비용, 판매 환급, 업그레이드 실패 처리를 같은 거래 계약으로 통합한다.
- 주요 결과: `EC-01`~`EC-08`, 총 투자액 환급, 입력 취소 불변.
- 종료 조건: 반복 추가/제거에서 골드가 증가하지 않는다.
- 전체 실행: 판매 확인 UX가 들어갈 때만 최소 실행.

### M4 - 레벨별 웨이브와 데이터 파이프라인

- 목표: `TD-003`의 6/7/8웨이브를 데이터 중심으로 구현한다.
- 주요 결과: `WaveManager` 레벨 선택, Factory, 다음 위협 데이터, 완료 판정.
- 종료 조건: 위협 첫 등장·재등장·총 수 하네스가 통과한다.
- 선행 조건: M1의 데이터/런타임 경계 결정.

### M5 - HUD·결과·게임플레이 UX

- 목표: 다음 위협, 편집 미리보기, 실패 원인, 결과 조언을 읽기 전용 View로 연결한다.
- 주요 결과: HUD 계약, 입력 명령, 결과 화면, 터치 구간 검증.
- 종료 조건: View가 Model을 변경하지 않고 핵심 선택을 화면에서 이해할 수 있다.
- 전체 실행: 필요. 입력과 렌더링이 주요 변경이다.

### M6 - 밸런스 및 릴리스 검증

- 목표: 후보 수치를 플레이 테스트와 결정적 시뮬레이션으로 조정한다.
- 주요 결과: 전략 다양성, 6~8웨이브, 약 20분 목표, 난이도 실패 신호 검증.
- 종료 조건: GDD의 후보값을 증거와 함께 확정하거나 재작업한다.
- 전체 실행: 플레이 테스트에 필요.

| 항목 | 상태 | 해소 기준 |
|---|---|---|
| 플레이어 방향과 핵심 루프 | 준비됨 | 기존 GDD 승인 범위 유지 |
| 실시간 경로 규칙 | 준비됨 | `TD-001` 정책과 `RT-*` 사례 |
| 경제·판매 정책 | 준비됨 | `TD-002` 정책과 `EC-*` 사례 |
| 레벨 웨이브 역할 | 준비됨 | `TD-003` 6/7/8웨이브 매트릭스 |
| 아키텍처 선택 | 미정 | 사용자 검토 후 ADR-001 수락 |
| 구현 작업 계획 | 미정 | ADR-001 후 각 마일스톤 작업 계획 작성 |

## 작업 규칙

1. 아키텍처 결정 전에 기능 구현을 시작하지 않는다.
2. 각 마일스톤에는 측정 가능한 종료 조건과 관련 ADR 링크가 있어야 한다.
3. 기존 기능을 옮길 때는 먼저 characterization harness를 작성한다.
4. 한 작업은 하나의 행동 경계만 변경한다.
5. 하네스가 가능한 변경은 전체 LÖVE 실행을 반복하지 않는다.
6. 밸런스 수치와 구조 리팩터링은 같은 작업에 섞지 않는다.

## 검증 전략

- 우선 하네스: 현재 Model 후보, 경로, 경제, 웨이브, 전투 모듈 단위·통합 테스트
- 정적 경계: Model에서 `love.*`와 draw 의존성 부재, View에서 상태 변경 부재
- 통합 검증: 고정 스텝 입력 스크립트의 결정적 결과
- 전체 실행: M2·M3의 입력 UX, M5의 HUD·터치·렌더링, M6 플레이 테스트에 한정

## 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 과도한 리팩터링 | 기능 개발 지연 | 한 마일스톤마다 파일과 외부 계약을 최소화 |
| View와 Model의 동시 변경 | 회귀 원인 불명확 | 읽기 전용 스냅샷을 먼저 도입 |
| Command 패턴 과용 | 작은 기능도 복잡화 | 편집·판매·업그레이드 거래에만 적용 |
| ECS 등 불필요한 프레임워크 | 학습 범위 이탈 | 유닛 규모 근거가 생길 때만 재검토 |
| 수치와 구조 동시 변경 | 실패 원인 분리 불가 | 구조 마일스톤에서 후보 수치 고정 유지 |
