# 타워 디펜스 개발 용어집

> 대상: `02_tower_defense` 기획·아키텍처·구현 문서
> 갱신 기준: 새로운 용어가 문서나 코드에 처음 등장할 때 함께 보강

## 사용 방법

- 약어는 처음 등장할 때 전체 영어 단어와 한국어 뜻을 함께 표기한다.
- 용어마다 정의뿐 아니라 이 프로젝트에서의 적용 예와 오해하기 쉬운 점을 적는다.
- 현재 수락된 아키텍처는
  [ADR-001](architecture/001-gameplay-architecture-review.md)과
  [결정적 Simulation Core + Command 아키텍처](architecture/002-deterministic-simulation-command-architecture.md)를
  따른다.
- 관련 문서의 줄이나 파일명은 구현 과정에서 바뀔 수 있으므로, 개념을 먼저
  이해하고 실제 파일은 세션 상태와 코드를 확인한다.

## 1. 문서와 의사결정

### ADR — Architecture Decision Record

**아키텍처 결정 기록**

중요한 기술 선택의 배경, 선택지, 결정, 근거, 결과, 재검토 조건을 남기는
문서다. 예를 들어 “왜 Scene 중심 구조, MVC, ECS 중 하나를 선택했는가”를
기록한다.

ADR은 단순 설계 설명서가 아니다. 선택하지 않은 대안과 그 이유까지 남겨서,
나중에 같은 논의를 처음부터 반복하지 않게 한다.

이 프로젝트의 [ADR-001](architecture/001-gameplay-architecture-review.md)은
결정적 Simulation Core, 원자적 Command/Transaction, 최소 MVC와 제한적
Layered/Hexagonal 경계를 수락한 상태다. 구현 계약은 후속 상세 설계 문서를
따른다.

### GDD — Game Design Document

**게임 디자인 문서**

플레이어 경험, 핵심 재미, 규칙, 콘텐츠, 난이도, 성공·실패 조건 같은 기획
기준을 기록한다. 세부 코드 구조와 구현 일정은 GDD에 넣지 않는 것이 좋다.

현재 프로젝트의 GDD는 다음처럼 사용한다.

- 플레이어에게 어떤 판단을 하게 할 것인가?
- 웨이브가 어떤 순서로 위협을 가르칠 것인가?
- 편집·판매 시 무엇이 허용되고 무엇이 거절되는가?
- 어떤 수치가 아직 가설인지 명시한다.

### Milestone

**마일스톤 / 단계 목표**

서로 연관된 여러 작업을 묶어, 그 기간에 남겨야 할 사용자·프로젝트 결과와
종료 조건을 정의한다. “이번 주에 파일 3개 수정”이 아니라 “원자적 편집을
헤드리스로 검증 가능하게 한다”처럼 결과 중심으로 표현한다.

마일스톤은 세션보다 크고, 하나의 기능보다 넓은 경우가 많다. 현재
[M0 구현 로드맵](planning/M0-implementation-roadmap.md)은 아키텍처 확정부터
밸런스 검증까지의 큰 순서를 다룬다.

### Work Plan

**작업 계획**

한 작업 또는 한 세션에서 무엇을 수정하고, 어떤 순서로 진행하며, 언제 완료로
판단할지를 정의한다. 허용 파일, 금지 범위, 검증 방법을 함께 적는다.

작업 계획은 미래 행동을 정의하고, worklog는 실제 수행 결과를 기록한다는 점이
다르다.

### Worklog

**작업 기록 / 세션 기록**

한 세션에서 실제로 무엇을 결정하고 변경했는지, 어떤 검증을 실행했는지,
무엇이 남았는지를 기록한다. 기존 기록을 덮어쓰지 않고 새 번호로 만든다.

worklog에는 “언젠가 하겠다”는 미래 약속보다 실제 사실을 남긴다. 다음 세션
프롬프트는 인계 수단으로 기록할 수 있다.

### RFC — Request for Comments

**의견 요청 문서**

아직 결론을 내리지 않은 제안이나 규격을 넓게 검토하기 위해 쓰는 문서다.
ADR은 주로 결정과 근거를 남기고, RFC는 결정을 앞둔 토론 자료에 가깝다.
현재 이 프로젝트는 ADR 검토 상태로 이 역할을 대신하고 있다.

## 2. 실행 구조와 아키텍처

### Architecture

**아키텍처 / 구조 설계**

프로그램의 주요 부분을 어떻게 나누고 연결할지 정하는 큰 구조다. 파일 개수나
폴더 정리만 뜻하지 않는다. 특히 다음을 정한다.

- 데이터와 상태를 누가 소유하는가?
- 입력이 게임 규칙에 어떻게 전달되는가?
- 화면은 상태를 어떻게 읽는가?
- 실패했을 때 어디에서 전체 변경을 막는가?
- 어떤 모듈을 독립적으로 테스트할 수 있는가?

### MVC — Model-View-Controller

**모델-뷰-컨트롤러**

입력, 상태와 규칙, 화면 표시를 세 책임으로 나누는 구조다.

#### Model

**모델**

게임의 상태와 규칙을 소유한다. 골드, 생명, 웨이브 진행, 맵 점유, 적과 타워
상태, 상태 전이 판단이 해당한다. Model은 LÖVE 그래픽, 마우스 입력, 파일
입출력에 직접 의존하지 않아야 한다.

#### View

**뷰**

상태를 화면에 표시한다. 적과 타워 그리기, HUD, 결과 화면, 미리보기 등이
해당한다. View는 화면을 만들기 위해 데이터를 읽지만 게임 규칙이나 Model
상태를 직접 변경하지 않는다.

#### Controller

**컨트롤러**

사용자 입력을 해석해 Model이 이해할 수 있는 명령으로 변환한다. “사용자가 이
셀을 탭했다”는 입력 사실을 “벽 후보 생성”, “판매 확정”, “웨이브 시작” 같은
의미 있는 명령으로 바꾼다.

현재 프로토타입의 `InputAdapter`와 Scene이 Controller의 일부 역할을 수행한다.
수락된 구조에서는 입력 의미 해석과 화면 전환을 Controller/Scene 경계로
점진적으로 옮기되, 코드 이동은 구현 마일스톤에서 수행한다.

### Scene

**장면 / 화면 단계**

타이틀, 레벨 선택, 게임플레이, 결과처럼 한 화면이나 게임 단계의 생명주기를
묶는 단위다. Scene은 화면 전환과 하위 부품의 연결을 담당할 수 있지만,
가능한 한 모든 게임 규칙의 단일 구현 위치가 되지 않도록 한다.

### Scene Stack

**장면 스택**

현재 Scene과 이전 Scene을 순서대로 보관하는 구조다. 새 Scene을 위에 쌓거나
현재 Scene을 교체·제거해 화면을 전환한다. 예를 들어 타이틀 Scene 위에 레벨
선택 Scene을 쌓았다가 결과 화면을 표시할 수 있다.

### Composition Root

**조립 지점**

애플리케이션에 필요한 객체와 모듈을 생성하고 서로 연결하는 위치다. 현재
프로젝트에서는 [main.lua](../src/main.lua)가 InputAdapter, SceneStack,
FixedTimestep, TitleScene 등의 시작 객체를 조립한다.

조립 지점이 있으면 도메인 모듈 내부에서 서로를 임의로 생성하지 않아도 된다.
테스트에서는 같은 위치 대신 다른 구현을 주입하기 쉬워진다.

### Layer

**계층**

비슷한 책임을 가진 모듈을 묶는 경계다. 일반적으로 상위 계층은 하위 계층의
계약을 사용하지만, 하위 계층은 화면이나 입력 기술을 몰라야 한다.

이 프로젝트에서는 다음 계층을 검토한다.

1. Scene / Composition
2. Controller
3. Model / Domain
4. View

계층은 폴더 이름만으로 보장되지 않는다. `require` 관계와 호출 계약도 같은
방향을 따라야 한다.

### Module

**모듈**

관련 함수와 데이터를 하나의 이름과 책임으로 묶은 코드 단위다. Lua에서는 보통
지역 테이블을 만들고 `return M`으로 공개한다.

좋은 모듈은 “무엇을 하는지” 한 문장으로 설명할 수 있고, 필요하지 않은 전역
상태에 의존하지 않는다.

## 3. 디자인 패턴

### Design Pattern

**디자인 패턴**

자주 나타나는 설계 문제와 그에 대한 검증된 해결 구조를 이름으로 부르는
방법이다. 패턴은 반드시 적용해야 하는 규칙이나 새 프레임워크가 아니다.
문제를 먼저 확인하고, 그 문제를 단순하게 해결할 때만 사용한다.

### Command Pattern

**명령 패턴**

사용자 요청을 “명령”이라는 단위로 표현하는 패턴이다. 벽 추가, 제거, 타워
판매, 업그레이드, 웨이브 시작을 각각 명령으로 만들 수 있다.

명령은 보통 다음 정보를 포함한다.

- 실행에 필요한 입력
- 실행 가능 여부 검사
- 성공했을 때 적용할 변경
- 실패 원인과 결과
- 필요하면 실행 취소 또는 롤백 정보

이 패턴은 버튼 클릭이 곧 여러 객체를 직접 수정하는 대신, 게임 규칙을 하나의
진입점으로 모으는 데 유용하다.

### Transaction

**트랜잭션 / 원자적 거래**

여러 상태 변경을 하나의 성공 단위로 처리하는 개념이다. 모든 변경이 성공하거나,
실패하면 이전 상태를 그대로 유지해야 한다.

타워 판매 예:

1. 새 경로 계산
2. 모든 지상 적의 합류 가능 여부 확인
3. 환급액 계산
4. 모든 조건 성공 시 타워 제거, 맵 변경, 골드 지급
5. 하나라도 실패하면 아무 변경도 하지 않음

트랜잭션의 핵심은 단순 호출 순서가 아니라 **실패 시 부분 적용을 허용하지 않는
것**이다.

### Simulation Core

**게임 시뮬레이션 핵심**

게임 상태와 규칙을 입력 장치, LÖVE 렌더링, 사운드와 분리해 실행하는 순수
도메인 계층이다. 고정 타임스텝마다 Command를 처리하고, 웨이브·이동·전투·경제·
승패를 갱신한다.

이 프로젝트에서 Simulation Core는 `GameState`, `GameSimulation`,
`CommandProcessor`, Domain System을 포함한다. 같은 초기 상태와 같은 Command
순서, 같은 fixed timestep이면 같은 최종 상태가 나온다.

### ViewData

**화면용 조회 데이터**

View가 렌더링하는 데 필요한 읽기 전용 데이터 묶음이다. 상태 변경 API가 아니라
화면 표현용 조회 계약이므로, HUD나 Renderer가 ViewData를 통해 골드나 적을
직접 수정하지 않는다.

전체 `GameState`를 매 프레임 복사해야 한다는 뜻은 아니다. 초기 구현에서는
읽기 전용 참조처럼 사용하되, View가 상태를 변경하지 않는다는 계약을 우선한다.

### Render Event

**렌더 이벤트 / 표현 이벤트**

Simulation이 이미 만든 상태 변화나 결과를 View와 효과 계층에 알리는 순서 있는
사실이다. 예를 들어 `TOWER_FIRED`, `COMMAND_REJECTED`, `ENEMY_DIED`가 있다.

Render Event는 게임 상태를 변경하는 요청이 아니라 시각·청각 표현용 출력이다.
전역 이벤트 버스를 의미하지 않으며, Simulation이 같은 tick에서 생성한 이벤트
목록을 명시적으로 반환하거나 전달해 처리한다.

### CommandResult

**명령 처리 결과**

Command 실행이 수락되었는지, 거절되었다면 어떤 코드 때문인지, 상태 revision과
Render Event가 무엇인지 반환하는 계약이다.

`false`나 `nil`만 반환하지 않고 `PATH_BLOCKED`, `INSUFFICIENT_GOLD`,
`NO_SAFE_JOIN` 같은 원인을 포함해야 실패 피드백과 헤드리스 검증을 할 수 있다.

### Atomicity

**원자성**

작업을 외부에서 관찰할 때 더 작은 부분으로 나누지 않고, 성공 또는 실패라는
하나의 결과로 보이게 하는 성질이다.

예를 들어 골드가 먼저 증가하고 타워는 나중에 제거되는 중간 상태를 다른
시스템이 관찰하면 안 된다. 원자적 거래는 후보 계산을 미리 하고 실제 상태를
한 번에 확정한다.

### Rollback

**롤백 / 되돌리기**

이미 변경한 상태를 이전 상태로 되돌리는 행위다. 가능하면 먼저 후보 상태를
검증해 실제 변경을 피하는 것이 더 단순하다. 이미 다수 객체를 변경한 뒤
롤백하는 방식은 누락 가능성이 있어 더 위험하다.

### Factory Pattern

**팩토리 패턴 / 생성 패턴**

객체 생성 규칙을 한곳에 모으고, 호출자는 생성 세부사항을 알지 않게 하는
패턴이다. 적 타입, 타워 타입, 웨이브 인스턴스를 정의 데이터와 생성 계약에
따라 만드는 경우 적합하다.

```text
정의 데이터 + 위치/웨이브 입력 → Factory → 객체
```

Factory를 사용하면 생성 코드를 줄일 수 있지만, 객체마다 특별한 팩토리를
만드는 것은 과잉 설계가 될 수 있다.

### Strategy Pattern

**전략 패턴**

같은 문제를 해결하는 알고리즘을 실행 중 교체 가능한 단위로 분리하는 패턴이다.
예를 들어 “타워 타겟 선정”을 가장 앞선 적, 가장 높은 체력, 가장 가까운 적
전략으로 나눌 수 있다.

현재 타워 디펜스에서는 타겟 규칙이 실제로 여러 개 필요해질 때 검토한다.
지금부터 Strategy 계층을 만들 필요는 없다.

### State Pattern

**상태 패턴**

객체의 상태별 행동을 별도 객체나 상태 정의로 나누는 패턴이다. build, wave,
gameover, victory가 더 많은 전이와 상태별 입력 규칙을 가지게 되면
유용하다. 현재 단순 상태 변수로 충분한지 먼저 확인한다.

## 4. 데이터와 코드 연결

### Data-driven Design

**데이터 중심 설계**

규칙이나 콘텐츠 값을 전용 데이터로 분리해 실행 코드는 형식과 동작만 담당하게
하는 방식이다. 웨이브의 적 타입, 수량, 간격을 큰 함수의 조건문 대신 테이블
데이터로 표현하는 것이 예다.

주의할 점은 데이터 중심 설계라고 모든 값을 런타임 설정으로 열어두는 뜻이
아니다. 검증되지 않은 값이나 해석이 어려운 문자열 로직도 피해야 한다.

### DTO — Data Transfer Object

**데이터 전달 객체**

시스템 경계 사이에서 전달할 데이터를 묶은 값이다. 이 프로젝트에서는 View에
보낼 읽기 전용 화면 데이터를 뜻할 수 있다.

HUD가 Scene 전체를 받는 대신 다음처럼 필요한 값만 받을 수 있다.

```lua
{
    gold = 150,
    lives = 20,
    currentWave = 2,
    totalWaves = 6,
    placeMode = "wall"
}
```

DTO의 목적은 화면을 위한 데이터를 제공하면서, HUD가 Model 객체 전체에 직접
접근해 수정하지 못하게 하는 것이다.

### Dependency

**의존성**

한 모듈이 다른 모듈의 기능이나 값을 필요로 하는 관계다.

```lua
local Enemy = require("03_game.enemy")
```

위 코드는 WaveManager가 Enemy 모듈에 의존한다는 뜻이다. 의존성은 나쁜 것이
아니지만, 어떤 모듈이 무엇에 의존하는지 명시적이고 추적 가능해야 한다.

### Coupling

**결합도**

모듈이 서로 얼마나 강하게 연결되어 있는지 나타낸다. 다른 모듈의 내부 구조를
직접 읽거나, 한 변경이 여러 모듈을 동시에 바꾸게 하면 결합도가 높다.

낮은 결합도는 모든 모듈이 혼자 작동한다는 뜻이 아니라, 공개 계약만 사용해
각 모듈이 내부를 바꿀 수 있다는 뜻이다.

### Cohesion

**응집도**

모듈 안의 기능들이 같은 목적과 책임에 얼마나 집중되어 있는지를 뜻한다.
`gameplayScene` 하나가 입력, 전투, 경제, 경로, 스폰, 화면을 모두 직접
처리하면 응집도가 낮아질 수 있다.

좋은 구조는 작은 모듈을 무조건 많이 만드는 것이 아니라, 하나의 모듈이 하나의
변경 이유를 갖도록 하는 것이다.

### Dependency Injection

**의존성 주입**

모듈 내부에서 필요한 객체를 직접 생성·검색하지 않고, 외부에서 생성자나
함수 인자로 전달받는 방법이다.

```lua
local controller = Controller.new(gameModel, inputAdapter)
```

장점은 테스트에서 같은 위치에 다른 구현을 넣을 수 있고, 모듈의 의존 관계가
명확해진다는 것이다. 단점은 작은 문제에도 생성자 인자가 늘어날 수 있다.

### Service Locator

**서비스 로케이터 / 전역 서비스 찾기**

필요한 객체를 중앙 레지스트리에서 문자열 이름으로 찾아오는 구조다. 사용이
편할 수 있지만 호출부에서 의존성이 드러나지 않아서 현재 프로젝트처럼 작은
코드에서는 피하는 편이 좋다.

### Event Bus

**이벤트 버스 / 사건 전달 중앙 통로**

여러 모듈이 이벤트를 발행하고 구독하는 구조다. 적 처치, 타워 설치, 웨이브
종료 같은 사건을 느슨하게 연결할 수 있다.

장점만 있는 구조는 아니다. 흐름이 호출 스택에 보이지 않아 디버깅이 어려워질
수 있으므로, 명시적 함수 호출로 충분한 현재 범위에서는 먼저 사용하지 않는다.

## 5. 게임 상태와 루프

### Game Loop

**게임 루프**

매 프레임 입력을 읽고, 상태를 갱신하고, 화면을 그리는 반복 구조다. 상태 변경
순서와 렌더링 순서가 안정적이어야 게임이 결정적으로 동작한다.

권장 큰 흐름:

```text
입력 수집 → 입력 해석 → Model update → 렌더링
```

### Fixed Timestep

**고정 타임스텝**

프레임 시간에 상관없이 일정한 시간 단위로 게임 상태를 갱신하는 방법이다.
예를 들어 1/60초씩 여러 번 `update`를 실행할 수 있다.

같은 입력과 같은 갱신 횟수가 같은 결과를 만들도록 해주는 중요한 결정성
기반이다. 렌더링 프레임 시간과 시뮬레이션 시간을 직접 섞지 않는다.

### Determinism

**결정성**

같은 초기 상태, 입력, 갱신 순서, 의사난수 조건에서 같은 결과가 나오는 성질이다.
타워 타겟, 스폰 순서, 적 위치, 골드, 승패가 반복 실행에서 같아야 한다.

결정성은 재현, 테스트, 밸런스 비교, 버그 추적에 중요하다.

### State Machine

**상태 기계**

시스템이 한 시점에 명확한 상태 하나에 있고, 정해진 사건에 의해서만 다른
상태로 전이하는 모델이다.

예:

```text
build → wave → build
build → wave → victory
build → wave → gameover
```

허용되지 않은 전이를 막으면 UI와 게임 규칙이 상태에 따라 어긋나는 문제를 줄일
수 있다.

### Input Snapshot

**입력 스냅샷**

한 갱신 구간에서 발생한 입력을 모아 읽기 쉬운 값으로 전달하는 데이터다.
직접적인 입력 장치 호출 대신 Controller나 Model 단계에서 같은 입력 구조를
재현할 수 있게 한다.

예: `tapped`, `tapX`, `tapY`가 한 스냅샷에 들어갈 수 있다.

### Preview

**미리보기 / 후보 상태**

사용자가 최종 확정하기 전에 결과를 임시 계산해 보여주는 단계다. 후보 경로,
예상 비용, 예상 환급, 실패 원인을 보여줄 수 있다.

미리보기는 실제 골드, 맵, 타워, 적 상태를 변경하지 않아야 한다. 취소하면
후보 상태도 버리고 원래 상태를 유지한다.

### Confirmation

**확정**

미리보기 후보를 실제 상태에 적용하는 단계다. 모든 조건이 다시 확인되고,
Transaction이 성공해야 맵·경제·적 상태가 함께 바뀐다.

## 6. 객체와 데이터 모델

### Entity

**엔터티 / 개체**

게임 안에서 구분 가능한 객체다. 적, 타워, 벽 또는 효과가 엔터티가 될 수 있다.
객체 지향 구현에서는 테이블과 메서드 객체로, ECS에서는 식별자와 컴포넌트
조합으로 표현할 수 있다.

### Component

**컴포넌트**

엔터티에 붙는 데이터 묶음이다. 위치, 체력, 이동 속도, 공격력 같은 단위다.
ECS 용어로 쓰이며 현재 일반 Lua 객체에서의 필드와 항상 동일한 뜻은 아니다.

### System

**시스템**

ECS에서 같은 종류의 컴포넌트를 가진 엔터티를 규칙에 따라 갱신하는 처리 단위다.
Movement System, Combat System, Spawn System 등이 예다.

### ECS — Entity-Component-System

**엔터티-컴포넌트-시스템**

게임 객체를 식별자(Entity), 데이터(Component), 처리(System)로 나누는
아키텍처다. 많은 동시 엔터티와 데이터 중심 반복 처리에 강점이 있다.

현재 프로젝트에서는 객체 수와 기능보다 ECS 기반 구조 비용이 더 커질 수 있어,
성능 근거가 생기기 전에는 비교 대상으로만 둔다.

### Domain

**도메인**

프로그램이 다루는 문제 영역과 그 고유 규칙이다. 이 게임에서는 미로 빌딩,
경로 탐색, 타워 공격, 웨이브, 생명, 골드, 판매가 도메인에 속한다.

Domain 모듈은 화면이 어떻게 생겼는지보다, 게임 규칙이 무엇인지 알아야 한다.

### Domain Model

**도메인 모델**

도메인의 개념과 규칙을 코드 안의 객체·함수·데이터 구조로 표현한 것이다.
예를 들어 “경로가 끊기면 편집을 거절한다”, “판매는 총 투자액의 일부를
환급한다” 같은 규칙이 Domain Model에 속한다.

### Read-only Snapshot

**읽기 전용 스냅샷**

특정 순간의 상태를 View나 로그에 전달하기 위해 만든 복사 또는 표현이다.
Lua에서는 실제 불변 객체가 기본 제공되지 않으므로, 원본 테이블을 넘기지 않고
필요한 값만 새 테이블에 복사하는 계약으로 이를 구현할 수 있다.

## 7. 테스트와 검증

### Harness

**하네스 / 시험 실행기**

모듈을 실행하고 입력·결과를 확인하기 위한 작은 테스트 프로그램이나 실행
환경이다. 현재 `*_harness.lua` 파일은 LÖVE 창 없이 경로, 웨이브, 경제 같은
규칙을 실행하는 하네스다.

### Headless Test

**헤드리스 테스트 / 창 없는 테스트**

게임 창, 그래픽 렌더링, 실제 입력 장치 없이 규칙과 상태 변화를 검증하는
테스트다. 빠르고 반복 가능하며 결정성 검증에 유리하다.

### Characterization Test

**특성 고정 테스트**

리팩터링 전에 현재 동작의 관찰 가능한 특징을 기록하는 테스트다. 코드가 더
올바른 구조로 이동해도 기존 정상 동작과 호환되는지 비교할 수 있다.

버그처럼 보이는 현재 동작도 의도적으로 바꾸기 전에는 특성으로 기록할 수
있다. 이 작업은 “현재 버그를 승인한다”는 뜻이 아니라, 변경을 구분하기 위한
기준선이다.

### Unit Test

**단위 테스트**

함수나 모듈 하나의 규칙을 주변 시스템과 분리해 검증한다. Pathfinder의 경로
탐색, Economy의 지출, Tower의 공격 선택 같은 검증이 예다.

### Integration Test

**통합 테스트**

둘 이상의 모듈이 연결될 때의 행동을 검증한다. 예를 들어 맵 편집이 경로와 적
합류, 골드에 동시에 성공하거나 모두 실패하는지를 확인한다.

### Regression Test

**회귀 테스트**

이전에 동작하던 기능이 새 변경으로 다시 깨지지 않았는지 확인하는 테스트다.
새 기능을 추가할 때 관련 기존 테스트를 함께 실행해야 한다.

### Test Harness First

**테스트 하네스 우선**

전체 게임을 매번 실행하기 전에 작은 하네스와 모듈·통합 테스트로 변경을 먼저
검증하는 원칙이다. 경로, 경제, 데이터, 결정성은 헤드리스로 확인할 수 있다.

입력, 렌더링, 프레임 타이밍처럼 창이 필요한 문제만 최소 횟수로 LÖVE 전체
실행을 사용한다.

### Baseline

**기준선**

변경 전 현재 결과를 저장하거나 확인 가능한 형태로 고정한 기준이다. 구조
변경 이후 같은 입력에서 같은 결과인지 비교할 수 있다.

### Smoke Test

**스모크 테스트**

최소한의 핵심 기능이 실행되고 치명적으로 깨지지 않는지 빠르게 확인하는
테스트다. 로그인이나 타이틀 진입, 레벨 선택, 웨이브 시작, 종료 판정처럼
넓지만 얕은 흐름에 적합하다.

## 8. 코드와 품질

### Refactoring

**리팩터링**

외부에서 관찰되는 동작을 유지하면서 코드 구조와 책임을 개선하는 작업이다.
아키텍처 정리는 리팩터링이지만, 새 기능이나 밸런스 수치를 동시에 바꾸면
회귀 원인을 구분하기 어렵다.

### Encapsulation

**캡슐화**

객체의 내부 상태와 변경 방법을 외부에서 감추고 공개 계약만 제공하는 원칙이다.
다른 모듈이 내부 테이블을 직접 수정하지 않게 하면 불변 조건을 지키기 쉽다.

### Invariant

**불변 조건**

어떤 동작이 일어나도 반드시 유지되어야 하는 조건이다.

예:

- 골드는 음수가 될 수 없다.
- 출구로 이어지는 지상 경로가 항상 유효하다.
- 판매 실패 시 타워와 골드가 그대로다.
- View는 Model을 수정하지 않는다.

### Contract

**계약**

함수나 모듈이 어떤 입력을 받고 어떤 조건에서 어떤 결과를 내며, 호출자와
무엇을 약속하는지 정의한 것이다. 예를 들어 `startWave(levelIndex)`는 잘못된
레벨이면 명시적인 실패를 반환해야 하는 계약을 가질 수 있다.

### API — Application Programming Interface

**애플리케이션 프로그래밍 인터페이스**

다른 코드가 모듈이나 서비스를 사용하도록 공개한 함수, 데이터, 규칙의 경계다.
외부 웹 서비스에만 API가 있는 것은 아니며, Lua 모듈의 공개 함수도 API다.

### Interface

**인터페이스**

모듈이나 객체가 외부에 제공하는 사용 방법과 기대 행동이다. Lua에서는 정식
언어 키워드가 아니더라도 함수 집합과 데이터 계약으로 표현한다.

### Abstraction

**추상화**

복잡한 세부사항을 숨기고 현재 문제에 필요한 의미만 노출하는 방식이다.
좋은 추상화는 변경 가능성을 줄이고 이름과 책임을 명확하게 만든다. 실제 사용
사례가 없는데 미래를 대비해 만든 추상화는 오히려 복잡도를 높인다.

### Overengineering

**과잉 설계**

현재 요구보다 많은 구조, 패턴, 설정, 파일을 먼저 만드는 것이다. 작은 게임에
큰 ECS 프레임워크나 범용 이벤트 시스템을 무근거로 도입하면 과잉 설계가 될 수
있다.

과잉 설계인지 판단하려면 “현재 GDD의 어떤 확인 사례를 해결하는가?”를 묻는다.

## 9. Lua 및 LÖVE 관련

### LuaJIT

**Lua Just-In-Time compiler**

Lua 코드를 Just-In-Time 방식으로 실행하는 고성능 런타임이다. LÖVE 11.5가
사용하는 Lua 환경과 호환되는 문법·표현을 중요하게 다뤄야 한다.

이 프로젝트에서는 Lua 5.1 호환 문법을 기준으로 한다.

### LÖVE

**LÖVE game framework**

Lua로 데스크톱·모바일 게임을 만드는 프레임워크다. 화면, 입력, 오디오,
파일 시스템과 게임 콜백인 `love.load`, `love.update`, `love.draw` 등을
제공한다.

게임 규칙 Model이 `love.*`에 직접 의존하지 않도록 분리하면 헤드리스 테스트가
가능해진다.

### Callback

**콜백 / 호출되는 함수**

특정 사건이 발생했을 때 프레임워크가 대신 호출하는 함수다. LÖVE의
`love.load`, `love.update(dt)`, `love.draw`가 대표적이다.

콜백이 길어지면 직접 로직을 구현하지 말고, Scene이나 Controller, Model의
계약을 호출하도록 구성한다.

### Virtual Resolution

**가상 해상도**

실제 화면 크기와 별개로 게임이 계산하고 그리는 기준 좌표계다. 여러 기기
크기에서 같은 배치와 터치 좌표를 사용할 수 있게 한다.

현재 프로젝트는 고정 기준 해상도와 변환 계층을 유지하며, Domain 좌표와 화면
좌표가 분리되는지를 함께 검토해야 한다.

### Implicit Global

**암묵적 전역**

`local` 선언 없이 변수에 값을 넣어 전역 테이블에 등록되는 상태다. Lua에서
전역을 실수로 생성하기 쉬우므로 변수와 의존성을 명시적으로 지역 선언해야
한다.

암묵적 전역은 모듈 간 보이지 않는 결합과 테스트 간 상태 오염을 만들 수 있다.

### Lua 5.1 Compatibility

**Lua 5.1 호환성**

코드가 Lua 5.1과 LuaJIT에서 지원되는 문법만 사용하도록 하는 기준이다.
`goto`, `table.unpack`, `//` 같은 새 문법·API를 사용하지 않는다.

## 10. 이 프로젝트의 주요 작업 용어

### Characterization Harness

**현재 동작 특성 확인 하네스**

아키텍처 변경 전에 현재 입력과 출력의 모습을 작은 시나리오로 고정하는
하네스다. Characterization Test와 Harness를 합친 표현이다.

### Implementation Roadmap

**구현 로드맵**

GDD 결정과 아키텍처가 기능 구현으로 이어지는 순서, 의존성, 마일스톤,
검증 전략을 연결한 계획이다. “어느 기능을 먼저 할지”뿐 아니라 “왜 그
선행 조건이 필요한지”를 설명한다.

### Gate

**게이트 / 승인 관문**

다음 단계로 넘어가기 위해 만족해야 하는 조건이다. 예를 들어 ADR 승인,
하네스 통과, 사용자 확인, 필수 문서 작성이 게이트가 될 수 있다.

게이트는 일정을 늦추기 위한 형식이 아니라, 비가역적인 변경을 증거 없이
시작하지 않게 하는 통제다.

### Scope

**범위**

현재 작업에서 바꾸는 것과 명시적으로 바꾸지 않는 것의 경계다. “이 세션에서
아키텍처만 검토하고 `src/`와 `tests/`는 수정하지 않는다”가 범위 선언이다.

명확한 범위는 관련 없는 버그를 고치거나, 밸런스와 구조 리팩터링을 한 번에
섞는 일을 막는다.

### Trade-off

**트레이드오프 / 상충 관계**

한 선택에서 얻는 이점과 함께 포기하거나 감수하는 비용이다. 예를 들어 MVC는
책임과 테스트를 명확히 하지만 파일·연결 코드가 늘어난다. ECS는 대규모
처리에 강하지만 작은 프로젝트에서는 학습과 구현 비용이 크다.

좋은 ADR은 장점만 나열하지 않고 트레이드오프를 함께 기록한다.

### Deferred Decision

**연기된 결정**

지금 만들 정보나 증거가 부족해 확정하지 않은 결정이다. “미정”과 비슷하지만,
결정을 무엇 때문에 연기했고 언제 다시 검토할지 기록한다는 점이 중요하다.

타워·적 최종 수치는 플레이 테스트가 없어서 현재 연기된 결정이다.

## 11. 용어 추가 규칙

새 용어는 다음 기준을 만족할 때 이 문서에 추가한다.

1. ADR, GDD, 작업 계획, 세션 인계에 처음 등장한다.
2. 구현자나 학습자가 약어 의미를 추측해야 한다.
3. 프로젝트 안에서 일반 용어와 다르게 사용하는 경우가 있다.
4. 선택지를 비교하거나 검증 절차를 이해하는 데 필요하다.

항목에는 가능하면 다음 내용을 포함한다.

- 전체 영어 단어와 한국어 뜻
- 한 문장 정의
- 프로젝트에서의 사용 예
- 자주 생기는 오해나 주의점
- 관련 패턴, 문서, 코드 링크
