## 검증 목록

1. 14개 현재 harness가 고정 순서로 한 번씩 실행된다.
2. 각 harness는 별도 Lua 프로세스에서 실행되어 module cache와 전역 `love`
   상태를 공유하지 않는다.
3. runner를 저장소 루트, `tests`, `tests/core`에서 실행해도 성공한다.
4. 의도적 실패 fixture의 원본 오류와 실패 harness 이름이 출력된다.
5. 의도적 실패는 0이 아닌 종료 코드로 반환되고 후속 harness를 실행하지
   않는다.
6. 전체 characterization 기준선은 79/79다.

## 회고

1. 하네스별 하위 프로세스는 공통 stub과 module cache 충돌 위험을 제거했다.
2. runner 기준 디렉터리와 harness 기준 디렉터리를 분리해 호출 위치와 기존
   상대 경로 계약을 동시에 보존했다.
3. 실패 fixture에서 Lua 5.1의 `os.execute` 종료값 `256`이 `os.exit(256)`에서
   성공 종료로 감싸질 수 있음을 발견하고 runner 실패를 `os.exit(1)`로
   정규화했다.
4. 후속 검토에서 Windows `\` 경로 구분자를 runner 시작 경로에서 `/`로
   정규화했다. POSIX와 Windows 소스 경로 모두 같은 디렉터리 계산을 사용한다.
5. 출력 flush를 추가해 `[RUN]`, 원본 오류, `[FAIL]`의 순서가 실행 순서와
   일치하게 했다.
6. `02_tower_defense/run.bat`의 기존 사용자 변경은 확인만 하고 건드리지
   않았다.

## 미해결 문제와 위험

- Windows 실제 shell에서 `cd /d`, 인용, Lua 실행 파일 전달 계약은 이 macOS
  세션에서 실행하지 못했다. 코드에는 Windows 분기를 포함했으며
  `TD_LUA_EXECUTABLE` 환경 변수로 실행 파일을 명시할 수 있다.
- 마지막 Wave 10 완료 후 `allWavesComplete`가 설정되지 않아 승리 대신 build로
  돌아가는 동작은 M1에서 발견한 후속 문제다. M1 characterization 범위에서는
  수정하지 않았다.
- M2는 GameState, CommandResult, Transaction을 도입하기 전에 M0과 상세 설계의
  현재 범위를 독립 착수 문서로 다시 확인해야 한다.
