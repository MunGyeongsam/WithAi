## 검증 목록

1. Map은 범위 밖, 점유 셀, 입구·출구, 유일 경로 차단 배치를 거절한다.
2. Map 제거는 wall/tower에서만 성공한다.
3. 잘못된 tower type은 `nil`, `getCost`는 `0`을 반환한다.
4. Economy의 골드 부족 지출은 gold/totalEarned/totalSpent를 바꾸지 않는다.
5. flying은 새 지상 경로를 무시하고 nil/빈 경로는 no-op이다.
6. Tower는 공중 제한, 사거리, 진행도 우선순위를 따른다.
7. Wave queue는 지연과 그룹 순서를 보존하며 마지막 스폰 뒤 다음 update에서
   `spawning=false`가 된다.
8. Level 1~3의 이름, 맵, 자원 초기값이 fingerprint와 일치한다.

## 회고

1. 현재 공개 API만으로 C항 1~9를 관찰해 source seam 없이 characterization을
   완성했다.
2. 반환값뿐 아니라 Economy 누적값, Map 셀 타입, Wave 완료 tick처럼 결과 상태를
   함께 fingerprint했다.
3. Wave 마지막 스폰 직후에는 `spawning=true`가 유지된다는 현재 동작 차이를
   별도 경계 계약으로 남겼다.
4. 첫 wave 하네스 실행에서 테스트 호출부의 괄호 누락을 구문 검사로 발견했고
   수정 후 전체 기준선을 재검증했다.
5. 후속 검토에서 `canPlace` false만 보던 경로 차단 시나리오를 실제
   `placeWall`/`placeTower` 실패와 경로 불변까지 확장했다.
6. Wave 그룹 순서 fixture를 `isWaveInProgress()==false`인 정상 완료 상태에서
   다음 웨이브를 시작하도록 정리했다.

## 미해결 문제와 위험

- wave completion은 마지막 적 스폰 직후가 아니라 다음 update에서
  `spawning=false`가 된다. M1은 현재 행동만 기록하며 수정하지 않았다.
- 기존 하네스의 실행 위치 의존 `package.path`는 작업 5 runner에서 정규화해야 한다.
- 실제 10웨이브 종료의 build 전이는 작업 3에서 발견한 별도 동작이며 M1 범위 밖이다.
- `02_tower_defense/run.bat`를 포함한 기존 사용자 변경은 건드리지 않았다.
