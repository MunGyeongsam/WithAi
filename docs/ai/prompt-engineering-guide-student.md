## 0. 왜 이렇게 해야 하나

- AI 는 대화에 오간 내용을 모두 받지만, **모두 똑같이 신경 쓰지는 않는다.** 대화가 길어지면 앞에서 말한 제약("Lua 5.1", "`local` 만")을 점점 무시한다.
- 여러 번 고친 코드의 옛 버전과 새 버전이 대화에 섞이면 AI 가 헷갈린다.
- Gemini 는 매우 많은 자료를 한 번에 받을 수 있다. 하지만 **많이 넣을 수 있다는 것과 잘 처리한다는 것은 다르다.** 관계없는 자료가 많을수록 엉뚱한 파일을 고치거나 없는 함수를 지어낸다.

## 1. 도구 고르기

| 하고 싶은 일 | 도구 |
|---|---|
| 개념 질문, 설계 토론, 패턴 비교, 프롬프트 다듬기 | **Gemini 앱** (채팅 + 스킬) |
| 실제 파일 수정, 테스트 실행, 여러 파일 작업 | **Antigravity** (에이전트) |

- Antigravity 무료 등급은 **주간 사용량 제한**이 있다. 설계와 질문은 Gemini 앱에서, 파일 수정은 Antigravity 에서 하면 사용량을 아낄 수 있다.
- Gemini CLI 와 Gemini Code Assist 는 개인 무료 사용이 종료됐다 (2026-06). Antigravity 를 쓴다.
- Gems 는 Skills 로 바뀌고 있다 (개인 계정: 2026-11-17 읽기 전용, 2026-12-17 삭제). 예전 Gem 은 자동으로 스킬로 옮겨지며, 옮겨진 스킬은 직접 확인하고 활성화해야 한다. 직접 다시 만들어도 된다. 학교 계정은 2027년에 전환된다.

## 2. 세션 운영: 한 세션에 한 태스크

**1 세션 = 1 태스크 = 커밋 1개 정도.** 태스크는 "테스트 하나나 실행 확인 한 번으로 끝났는지 판단할 수 있는 목표"다.

| 좋은 태스크 | 너무 큰 태스크 |
|---|---|
| 적 FSM 상태 전이 구현 + 전이 테스트 | 적 AI 전부 만들기 |
| 웨이브 문자열 `"A3 B2"` 파서 + 테스트 | 웨이브 + 점수판 + 보스 |
| GameView 에 폭발 연출 추가 | View 전체 리팩터링 |

**새 세션을 열어야 하는 신호**
- 태스크를 끝내고 커밋했다 → **무조건 새 세션**
- AI 가 이미 지적한 실수를 반복한다
- AI 가 처음 준 제약을 어긴다 (Model 안의 `love.graphics` 등)
- 대화가 15~20턴을 넘었다
- 주제가 바뀌었다
- 같은 버그를 3번 고쳐도 안 된다 → 새 세션에서 처음부터 설명하는 편이 빠르다

**인계 메모:** 세션을 닫기 전에 요청한다. 스킬 `worklog-writer` 를 쓰면 자동으로 양식이 맞는다.
```
지금까지 작업을 다음 세션 인계 메모로 정리해 줘.
1) 완료 2) 바뀐 파일·핵심 함수 3) 정한 규칙 4) 남은 문제 5) 다음 태스크
코드 없이 10줄 이내.
```
새 세션의 첫 프롬프트에 붙여 넣고, 작업 로그에도 남긴다.

**길게 써도 되는 예외:** 코드를 만들지 않는 설계 토론, 에러 하나를 끝까지 추적하는 디버깅 (해결되면 바로 닫기).

## 3. 참조 파일: 개수보다 역할

| 역할 | 권장 개수 | 예 |
|---|---|---|
| 수정 대상 | 1~2 | `models/EnemyModel.lua` |
| 계약/인터페이스 (읽기 전용) | 1~3 | `models/GameModel.lua` |
| 규칙 문서 | 1 | `AGENTS.md` (스킬로 대체 가능) |
| 스타일 예시 | 0~1 | 잘 만든 `PlayerModel.lua` |

**코드 생성은 3~5개, 최대 6개 정도가 적당하다.**

| 상황 | 파일 양 |
|---|---|
| 기능 구현, 버그 수정 | 위 표 기준 (최소) |
| 에러 해결 | 에러 난 파일 + **에러 메시지 전문** + 호출한 쪽 |
| 설계·구조 질문 | 폴더 구조 + 핵심 파일. 전체도 가능하지만 "코드는 만들지 마" 명시 |

**지킬 것**
1. 파일 경로를 머리말로: `-- 파일: models/EnemyModel.lua`
2. 읽기 전용 표시: "GameModel.lua 는 참고만, 수정 금지"
3. 최신 버전만. 옛 버전이 대화에 남아 있으면 새 세션을 연다.
4. 긴 파일은 필요한 함수만.

**Antigravity 에서는** 에이전트가 파일을 알아서 읽는다. 대신 **수정 범위를 제한**하는 것이 중요하다: "수정 허용: `models/EnemyModel.lua`, `tests/enemy_fsm_test.lua`. 그 외 수정 금지."

## 4. 프롬프트 6요소 템플릿

```
[맥락] 무엇을 만들고 있고 지금 어디까지 했는지
[목표] 이번에 할 일 1개
[참조] 파일 목록과 역할 (수정 대상 / 읽기 전용)
[제약] 언어 버전, 구조 규칙, 금지 사항
[출력 형식] 무엇을 어떤 형태로
[검증] 완료 확인 방법
```

**나쁜 예:** `적 AI 만들어줘`

**좋은 예:**
```
[맥락] LÖVE 11.5 + Lua 5.1(LuaJIT) 갤러그를 MVC 로 만들고 있다.
Model 은 순수 Lua 이고 헤드리스 테스트로 검증한다.
[목표] 적 AI 를 State 패턴으로 구현한다. 상태: idle → chase → attack → flee
[참조] models/EnemyModel.lua (수정), models/GameModel.lua (읽기 전용),
tests/helper.lua (테스트 스타일 참고)
[제약] Lua 5.1 문법만, 모든 변수 local, models/ 에서 love.* 금지,
상태는 { enter, update, exit } 테이블
[출력 형식] 1) 상태 전이표만 먼저 보여 주고 멈춰라. 2) 승인 후 바뀐 파일과 변경 이유 3줄
[검증] 전이 조건마다 tests/enemy_fsm_test.lua 에 테스트 1개
```

스킬 `prompt-improver` 에 내 프롬프트를 넣으면 6요소 진단과 개선안을 받을 수 있다. 상황별 예시 10쌍은 [프롬프트 예시집](../../lua_tuto/mvc/skill_agent/프롬프트_예시집.md).

## 5. 효과가 큰 기법 8가지

| # | 기법 | 문구 예 | 효과 |
|---|---|---|---|
| 1 | 계획 먼저 | "코드 전에 설계와 파일 목록만" | 방향이 틀리면 싸게 고친다 |
| 2 | 질문 먼저 | "모호하면 코드 전에 질문부터" | 추측으로 빈칸을 채우지 않게 |
| 3 | 테스트 먼저 | "이 동작의 테스트부터 작성" | 완료 기준이 생긴다 |
| 4 | 예시 주기 | "PlayerModel.lua 와 같은 스타일로" | 말보다 정확하다 |
| 5 | 금지 명시 | "다른 함수는 건드리지 마" | 멀쩡한 코드를 바꾸지 않게 |
| 6 | 변경분만 받기 | "바뀐 함수만, 변경 표시" | 검토와 기록이 쉽다 |
| 7 | 자기 검토 | "방금 코드가 [제약]을 어긴 곳을 줄 번호로" | 스스로 많이 찾아낸다 |
| 8 | 대안 비교 | "방법 2~3개를 장단점 표로" | 설계 근거가 보고서에 남는다 |

**에러를 물을 때**
```
[실행 결과] (에러 메시지와 스택 트레이스 전문)
[관련 코드] (에러 난 줄 앞뒤 함수)
[시도한 것] (이미 해 본 것)
[질문] 원인을 먼저 설명하고, 수정은 최소한으로
```
"안 돼요", "고쳐 줘" 만 보내는 것이 가장 나쁜 프롬프트다.

## 6. 스킬 · 에이전트 키트 쓰기

키트 위치와 설치법: [skill_agent/README.md](../../lua_tuto/mvc/skill_agent/README.md)

| 언제 | 쓸 것 |
|---|---|
| Lua 코드를 받았을 때 | 스킬 `lua51-guard` |
| 새 코드를 어느 폴더에 둘지 고민될 때 | 스킬 `mvc-boundary` |
| 패턴 선택이 고민될 때 | 스킬 `game-ai-pattern-coach` (힌트만 준다) |
| 구현 전에 | 스킬 `headless-test-writer` |
| 프롬프트가 잘 안 먹힐 때 | 스킬 `prompt-improver` |
| 세션 끝 | 스킬 `worklog-writer` |
| (Antigravity) 세션 시작/끝 | 워크플로 `/start-session`, `/end-session` |
| (Antigravity) 계획 / 리뷰 / 테스트 | 에이전트 `planner`, `lua-reviewer`, `test-runner` |
| (Antigravity) 프롬프트를 단계별로 다듬을 때 | 워크플로 `/prompt-expert` |
| Lua 문법·메타테이블·모듈 설계가 궁금할 때 | 스킬 `lua-expert` |
| 폴더·모듈 구조를 정리할 때 / 새 기능 골격이 필요할 때 | 스킬 `love2d-architect` / `love2d-feature-scaffold` |
| (Antigravity) 위 작업을 직접 수정까지 맡길 때 | 에이전트 `lua-expert`, `love2d-architect`, `love2d-feature-scaffold` (수정 가능하므로 **수정 허용 파일** 필수) |

**에이전트(Antigravity) 추가 수칙**
- 작업 전에 커밋해 둔다. 되돌리기가 쉽다.
- 프롬프트에 **수정 허용 파일**을 적는다.
- "기존 테스트를 삭제하거나 약하게 만들지 마" 를 넣는다.
- 끝나면 반드시 `git diff` 로 직접 확인하고 커밋한다.
- 에이전트가 명령 실행 승인을 요청하면 **무슨 명령인지 읽고** 승인한다. 테스트 실행(`luajit ...`)이 아닌 삭제·설치·git 조작 명령은 거절한다.

**과제:** 자기 프로젝트용 스킬을 1개 이상 직접 만들고, 적용 전후를 비교해 로그에 남긴다. 방법은 [작성 가이드](../../lua_tuto/mvc/skill_agent/작성_가이드.md) 5절.

## 7. AI 가 자주 틀리는 Lua / LÖVE 함정

AI 결과를 **거절하거나 고친 기록**은 작업 로그에서 중요한 점수다. 아래 표로 점검한다.

| 함정 | AI 가 쓰는 코드 | 올바른 코드 |
|---|---|---|
| 정수 나눗셈 | `a // b` | `math.floor(a / b)` |
| 언패킹 | `table.unpack(t)` | `unpack(t)` |
| 같지 않음 | `a != b` | `a ~= b` |
| 0-based 반복 | `for i = 0, #t - 1` | `for i = 1, #t` |
| 전역 누수 | `count = 0` | `local count = 0` |
| 색상 범위 | `setColor(255, 0, 0)` | `setColor(1, 0, 0)` |
| 5.2+ 문법·라이브러리 | `<const>`, `goto`, 전역 `utf8` | 쓰지 않는다 (`utf8` 이 필요하면 View 에서 `require("utf8")`) |
| 콜론/점 | `obj.method()` | `obj:method()` |
| MVC 위반 | Model 안의 `love.graphics` | View 로 옮긴다 |

## 8. 피해야 할 습관

1. "게임 다 만들어 줘" — 이해할 수 없고 로그에 쓸 것도 없다.
2. 이해 없이 복사·붙여넣기 — 보고서 설명 문항에 내 코드로 답하지 못하면 감점.
3. 한 세션에 계속 덧붙이기 — 30턴째엔 AI 가 처음 규칙을 잊는다.
4. 다시 생성 버튼만 누르기 — 무엇이 틀렸는지 말해야 나아진다.
5. 에러를 요약해서 보내기 — 원문 그대로 붙인다.
6. 개인정보·비밀 넣기 — 학번, 비밀번호, API 키는 넣지 않는다.

## 9. 작업 로그 양식 (`worklogs/NNN_YYYY-MM-DD_session.md`)

**최소 요건:** 프롬프트 기록 10개 이상, 그중 **거절 또는 수정 사례 3개 이상.** 실패 기록이 있어야 자연스럽다.

```markdown
## 프롬프트 기록 #3
- 시각 / 커밋: 14:20 / a1b2c3d
- 도구: Gemini 앱 / Antigravity (사용한 스킬·에이전트)
- 목적: 적 FSM 을 State 패턴으로 분리
- 프롬프트 원문:
  > (그대로 붙여넣기)
- AI 결과 요약:
- 판정: 채택 / 수정 후 채택 / 거절
- 문제점: EnemyModel.lua:12 전역 변수 state 누수
- 다음 프롬프트에서 바꾼 점: "모든 변수는 local, Model 에서 love.* 금지" 추가
```

**로그 채점 (각 과목 10점)**

| 세부 항목 | 점수 | 게임시스템설계 | 게임인공지능 |
|---|---|---|---|
| 프롬프트 원문 기록 | 3 | Lua 5.1, `local` 같은 제약을 명시했나 | 패턴명, 책임, 경계를 명시했나 |
| 개선 이력 (Before → After) | 3 | 문법·런타임 오류로 프롬프트를 고쳤나 | 구조 오류로 지시를 고쳤나 |
| 거절·수정 사례 | 2 | Lua 함정을 잡아냈나 | MVC 경계 위반을 잡아냈나 |
| 회고 | 2 | AI 에 맡긴 것 / 직접 한 것 | 다음에 프롬프트를 어떻게 바꿀지 |

- 커밋 해시를 적어 git 이력과 맞춰 본다.

## 10. 보내기 전 30초 체크리스트
