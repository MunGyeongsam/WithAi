# 졸업을 앞둔 여러분에게 — AI 시대, 좁은 문 앞에서 계속 단련하는 법

## 이 문서의 목적
- AI가 바꾸고 있는 개발 현장을 **있는 그대로** 바라본다
- 신입 채용이 좁은 시기를 **버티는 것이 아니라 성장하는 기간**으로 쓰는 방법을 정리한다
- 졸업 후 3~12개월 동안 스스로 돌릴 수 있는 **단련 루틴**을 제시한다

> 이 문서는 정답이 아니라 출발점입니다. 읽고 나서 나에게 맞게 고쳐 쓰세요.

---

## 1. 현실 인식: 무엇이 바뀌었나

### 솔직한 현재 상황
- 신입 채용 공고 수가 줄었고, 경력직 선호가 강해졌습니다.
- "간단한 코드 작성"은 AI가 빠르게 해내기 때문에, 그 일만 할 수 있는 신입의 가치는 낮아졌습니다.
- 반대로 **AI를 잘 다루면서 결과물을 책임질 수 있는 사람**의 가치는 올라갔습니다.

### 그래서 무엇이 중요해졌나
| 예전에 중요했던 것 | 지금 더 중요해진 것 |
|---|---|
| 문법을 많이 아는 것 | 코드를 **읽고 판단하는** 능력 |
| 빨리 타이핑하는 것 | 문제를 **정의하고 쪼개는** 능력 |
| 기능을 완성하는 것 | 동작을 **검증하고 설명하는** 능력 |
| 혼자 잘하는 것 | AI·사람과 **협업하고 소통하는** 능력 |

> 💡 핵심 한 줄: **"AI가 짠 코드를 내가 책임질 수 있는가?"** 이 질문에 "예"라고 답할 수 있는 사람이 되는 것이 목표입니다.

## 2. 마음가짐: 좁은 문 앞에서

1. **취업 준비 기간도 경력이다.**
   공백기가 아니라 "독립 개발 기간"으로 만드세요. 무엇을 만들고 무엇을 배웠는지 기록이 있으면 면접에서 그대로 이야기가 됩니다.
2. **비교 대상은 어제의 나.**
   SNS의 합격 소식과 비교하면 지칩니다. 지난달보다 나아졌는지만 보세요.
3. **불합격은 데이터다.**
   떨어진 이유를 추측이라도 적어 두고, 다음 지원에서 하나씩 고칩니다.
4. **길게 보고 체력을 아낀다.**
   6개월 이상 걸릴 수 있다고 가정하고, 지속 가능한 속도로 계획하세요. 수면·운동·사람 만나기도 루틴에 넣습니다.
5. **첫 직장이 마지막 직장은 아니다.**
   원하는 회사가 아니더라도, 실제 코드를 배포하고 유지보수해 보는 경험은 큰 자산입니다. 인턴·계약직·작은 스튜디오·인접 직군(QA, 툴 개발, 기술 지원)도 진지하게 고려하세요.

## 3. 무엇을 단련할까: 5가지 근육

### ① 기초 체력 — AI 없이도 설명할 수 있는 수준
- 자료구조·알고리즘, 메모리, 동시성, 네트워크, 자료형의 동작 원리
- C/C++의 포인터·메모리, C#의 참조/값 타입·GC, Lua의 테이블·클로저·메타테이블을 **남에게 설명**할 수 있는지 점검
- 연습법: 주 1회, AI 없이 작은 문제를 풀고 → 풀이를 AI와 비교 → 차이를 기록

### ② 읽는 힘 — 남이 쓴(AI가 쓴) 코드를 이해하기
- 오픈소스 프로젝트의 코드를 읽고 구조를 그림으로 정리
- AI가 생성한 코드를 **한 줄씩 설명**하는 연습 (설명 못 하는 줄 = 공부할 곳)
- 연습법: 관심 있는 오픈소스의 이슈 하나를 골라 원인을 추적해 보기

### ③ 검증하는 힘 — "돌아간다"가 아니라 "맞다"를 증명하기
- 테스트를 먼저 쓰고 구현하는 습관 (우리 수업의 **테스트 하네스 우선** 원칙)
- 버그를 만나면 **재현 → 원인 → 수정 → 재발 방지 테스트** 순서로 처리
- 연습법: 내 프로젝트의 버그 하나마다 테스트 하나를 추가

### ④ 설계하는 힘 — 구조를 잡고 경계를 지키기
- 모듈 분리, 의존성 방향, 책임 경계(MVC, update/draw 분리 등)
- "왜 이렇게 나눴는가"를 문서로 남기기 (설계 결정 기록)
- 연습법: 완성한 프로젝트를 리팩터링하며 전·후 구조를 비교해 정리

### ⑤ AI 협업 능력 — 도구를 부리는 사람 되기
- 맥락·목표·제약·출력 형식·검증 방법을 담은 프롬프트 작성 ([prompt-engineering-guide-student.md](./prompt-engineering-guide-student.md) 참고)
- AI 결과를 그대로 받지 않고 **의심 → 확인 → 수정**하는 습관
- 에이전트·스킬·규칙 파일처럼 **AI 작업 환경을 설계**하는 경험 (이 저장소의 `.github/agents`, `.github/skills` 구조가 좋은 예)

## 4. AI 활용 3단계 — 배우는 주제마다 적용하기

| 단계 | 방식 | 언제 |
|---|---|---|
| 1단계: 혼자 | AI 없이 직접 구현 | 처음 배우는 개념, 기초 문제 |
| 2단계: 튜터 | "왜?", "힌트만" 요청 | 막혔을 때, 개념 확인 |
| 3단계: 동료 | 구현을 맡기고 내가 검증·책임 | 이미 이해한 영역, 반복 작업 |

> ⚠️ 1단계를 건너뛰면 3단계에서 AI의 실수를 잡아내지 못합니다.

| 요일 | 활동 | 시간 |
|---|---|---|

## 6. 포트폴리오: "AI로 만들었다"보다 "내가 판단했다"를 보여주기

좋은 포트폴리오에 들어갈 것:
- **완성된 결과물** 1~2개 (작아도 끝까지 만든 것, 플레이·실행 가능한 빌드나 영상 링크. 자세한 구성은 10장 참고)
- **README**: 문제 정의 → 설계 결정 → 어려웠던 점 → 해결 과정
- **테스트**와 검증 방법
- **커밋·작업 로그 이력**: 꾸준함과 사고 과정이 드러나게
- **AI 활용 방식 설명**: 어디에 AI를 썼고, 어디서 AI가 틀렸고, 어떻게 잡아냈는지

피해야 할 것:
- 설명할 수 없는 코드
- 튜토리얼을 그대로 따라 만든 프로젝트만 나열
- 미완성 프로젝트 여러 개

## 9. 꾸준히 단련할 분야 — 수학과 글쓰기는 여전히 중요할까?

### 결론: 둘 다 더 중요해질 가능성이 크다. 단, 이유가 바뀌었다

| | 예전에 중요했던 이유 | 지금 중요한 이유 |
|---|---|---|
| 수학 | 직접 계산하고 구현하려고 | AI 결과가 맞는지 **판단하고**, 문제를 **모델링하려고** |
| 글쓰기 | 문서와 보고서를 작성하려고 | **생각을 정리하고**, AI와 사람에게 **정확히 지시하려고** |

### 수학 — "판단의 근거"
- **왜 필요한가:** AI는 계산은 잘하지만 "이 문제를 어떤 수학으로 풀지"는 사람이 정해야 합니다. 게임만 봐도 벡터, 행렬, 확률(드롭률, 밸런스), 물리, 최적화가 핵심입니다. 개념을 모르면 AI가 틀린 공식을 써도 알아채지 못합니다.
- **회의적 관점도 있다:** 손 계산 능력의 가치는 줄었고, 모든 개발자에게 깊은 수학이 필요하지도 않습니다.
- **어디에 집중할까:** 계산력보다 **개념 이해와 모델링**입니다. 선형대수, 확률·통계, 이산수학(그래프, 논리), 기초 미적분의 *의미*를 아는 수준이면 충분합니다. AI 분야로 가려면 통계와 선형대수를 더 깊게 하세요.
- **연습법:** AI가 준 공식을 "왜 이 식인가" 그림이나 코드로 직접 확인하기 (예: 충돌 판정 공식을 시각화해 보기)

### 글쓰기 — "생각의 증거"
- **생각의 도구:** 글로 쓰지 못하는 것은 대개 아직 이해하지 못한 것입니다.
- **AI 시대의 프로그래밍 언어:** 프롬프트, 스펙, 설계 문서, 이슈와 PR 설명이 사실상 AI와 동료에게 주는 "코드"입니다. 모호하게 쓰면 결과도 모호합니다.
- **회의적 관점도 있다:** 문장을 다듬는 일은 AI가 잘하므로 "예쁜 문장"의 가치는 낮아졌습니다.
- **어디에 집중할까:** **구조화**(무엇을, 왜, 어떤 순서로)와 **간결함**입니다. 문장 다듬기는 AI에게 맡겨도 됩니다.
- **취업 관점:** 경력을 증명하기 어려운 신입에게 잘 쓴 기술 블로그, README, 회고는 실력을 보여주는 가장 확실한 증거입니다.

### 그 밖에 꾸준히 단련할 분야

| 분류 | 분야 | 이유 |
|---|---|---|
| 오래 가치가 유지되는 기반 | 컴퓨터 구조·운영체제, 자료구조·알고리즘, 네트워크·DB 기초, 디버깅 | 10년 뒤에도 유효할 가능성이 높고, AI가 자주 헤매는 영역 |
| AI 시대에 새로 중요해진 능력 | 검증·테스트 설계, 시스템 설계, AI 도구 활용과 작업 환경 설계, 보안 감각 | AI 결과를 판단하고 책임지는 데 필요 |
| 사람과 관련된 능력 | 문제 정의, 소통·협업, 영어 읽기 | 자동화가 가장 어렵고, 최신 정보는 대부분 영어 |
| 도메인 지식 | 게임 디자인, 재미의 원리, 플레이어 심리 등 | "코딩 + 어떤 분야" 조합은 대체하기 어려움 |
| 배우는 방법 자체 | 공식 문서 → 작은 예제 → 실제 적용 | 기술은 바뀌어도 이 능력은 계속 쓰임 |

### 우선순위를 정하는 세 가지 질문
1. **10년 뒤에도 유효할까?** 그렇다면 꾸준히 합니다. (수학, 글쓰기, CS 기초)
2. **AI 결과를 판단하는 데 필요할까?** 그렇다면 우선합니다. (검증, 설계, 디버깅)
3. **지금 취업에 바로 필요할까?** 그렇다면 단기로 집중합니다. (특정 엔진, 프레임워크)

> 💡 비율 예시: **기반 50%, 실전 프로젝트 30%, 최신 도구 탐색 20%.** 유행만 좇으면 쉽게 지치고, 기반만 붙잡으면 시장과 멀어집니다.

## 10. 우리가 해 온 기술로 단련하기 — C/C++ · C# · Unity · LÖVE2D/Lua

여러분은 **C/C++, C#** 을 중심으로 배웠고, 팀 프로젝트는 **Unity + C#**, 바이브 코딩은 **LÖVE2D + Lua** 로 경험했습니다. 이 조합 자체가 이미 좋은 출발점입니다.

### 우리 조합의 강점
| 경험 | 강점 | 면접에서 이렇게 말할 수 있다 |
|---|---|---|
| C/C++ | 메모리, 포인터, 성능을 몸으로 이해 | "할당과 캐시를 의식하며 코드를 짭니다" |
| C# + Unity | 실제 업계에서 가장 많이 쓰는 엔진 경험, 팀 협업 | "팀 프로젝트에서 ○○ 시스템을 맡아 완성했습니다" |
| LÖVE2D + Lua | 엔진 없이 게임 루프·구조를 직접 설계, AI 협업 개발 | "AI와 함께 개발하되 테스트와 구조로 품질을 지켰습니다" |
| 여러 언어 경험 | 언어가 바뀌어도 원리로 적응하는 힘 | "새 언어·엔진에 빠르게 적응할 수 있습니다" |

> 💡 **엔진이 있는 개발(Unity)과 엔진 없는 개발(LÖVE2D)을 모두 해 봤다**는 점은 "엔진이 내부에서 무엇을 해 주는지 안다"는 뜻입니다. 이 점을 적극적으로 어필하세요.

### 언어·기술별로 계속 단련할 것

**C/C++ — 기반 체력**
- 메모리 관리(스택/힙, 소유권), 스마트 포인터, RAII, 이동 의미론 같은 모던 C++ 기초
- 자료구조를 직접 구현해 보고, 캐시 친화적인 데이터 배치 이해하기
- 왜 중요한가: AI가 만든 C++ 코드의 메모리 버그와 미정의 동작은 **사람이 잡아야** 합니다. 엔진, 서버, 클라이언트 프로그래머 직군에서 꾸준히 확인하는 역량입니다.

**C# — 실무 언어**
- 값/참조 타입, 박싱, GC 동작과 할당 줄이기, `async/await`, LINQ의 비용
- 인터페이스와 이벤트를 활용한 설계, SOLID 원칙을 "외우기"가 아니라 "써 보기"
- 왜 중요한가: Unity뿐 아니라 툴 개발, 서버(.NET)로도 이어지는 언어입니다.

**Unity — 취업 주력**
- **구조:** MonoBehaviour에 다 넣지 않기. ScriptableObject, 이벤트, 상태 패턴으로 책임 나누기
- **성능:** Profiler로 GC 할당·드로우콜·프레임 시간을 **측정하고 개선한 경험** (전·후 수치를 기록)
- **테스트:** Unity Test Framework(EditMode/PlayMode)로 핵심 로직 테스트 작성. LÖVE2D에서 익힌 **테스트 하네스 우선 습관**을 그대로 옮기기
- **협업:** Git으로 씬·프리팹 충돌 관리, 브랜치 전략, 코드 리뷰 경험
- **AI 활용:** AI가 짠 Unity 코드는 낡은 API나 `Update()` 안의 불필요한 할당·`GetComponent` 호출이 섞이기 쉽습니다. **Profiler와 공식 문서로 검증**하는 습관을 들이세요.

**LÖVE2D/Lua — 원리와 AI 협업의 연습장**
- 작은 프로토타입을 빠르게 만들어 **게임 아이디어를 검증**하는 도구로 계속 활용
- 게임 루프, 충돌, 씬 관리, ECS를 직접 구현해 본 경험을 **Unity 개념과 연결해 설명**하기
  (예: `love.update/draw` ↔ `Update/OnGUI·렌더링`, 직접 만든 충돌 ↔ Physics/Collider)
- 바이브 코딩 기말과제의 **작업 로그, 에이전트·스킬 설정, 테스트**는 "AI와 일하는 방식"을 보여주는 좋은 포트폴리오 자료입니다.

### 게임 수학 · 그래픽스 API · Windows 프로그래밍은 필요할까?

**결론: 셋 다 필요하지만, 깊이와 우선순위는 다르다**

| 분야 | 우선순위 | 권장 깊이 |
|---|---|---|
| 게임 수학 | ⭐⭐⭐ **필수** | 개념 이해 + 직접 구현 |
| 그래픽스 API (OpenGL/DirectX) | ⭐⭐ **목표 직군에 따라** | 기본 파이프라인을 직접 한 번 구현 |
| Windows 프로그래밍 (Win32) | ⭐ **선택** | 메시지 루프와 OS 기초 개념 정도 |

**게임 수학 — 필수**
- 벡터, 행렬, 쿼터니언, 좌표계 변환, 충돌, 보간, 확률은 엔진과 장르에 관계없이 매일 씁니다.
- AI가 가장 그럴듯하게 틀리는 영역입니다. 좌표계(왼손/오른손), 행렬 곱 순서, 회전 순서 실수를 알아보려면 개념을 알아야 합니다.
- 클라이언트 면접 단골 주제입니다(내적·외적의 의미, 시야각 판정, 반사 벡터 등).
- 학습법: Unity의 `Vector3`, `Quaternion`, `Matrix4x4`를 그냥 쓰지 말고 **C++이나 Lua로 직접 구현**해 보기. LÖVE2D에서 2D 회전, 충돌, 카메라를 수학으로 만들어 보는 것이 좋은 연습입니다.

**그래픽스 API (OpenGL / DirectX) — 목표 직군에 따라**
- 찬성: 렌더링 파이프라인(정점 → 래스터화 → 픽셀, 셰이더, 버퍼, 드로우콜)을 알면 Unity 최적화의 **근거**가 생깁니다. 엔진·그래픽스 프로그래머, 테크니컬 아티스트에게는 사실상 필수이고, 저수준 경험이 있는 신입은 드물어서 차별점이 됩니다.
- 회의: 대부분의 클라이언트 업무는 엔진 위에서 이루어집니다. DX12나 Vulkan은 학습 비용이 매우 커서 다른 준비가 밀릴 수 있습니다.
- 권장: **OpenGL(또는 DX11)로 "삼각형 → 텍스처 → 카메라 → 간단한 조명"까지 한 번 구현**하면 충분합니다. 원리는 같으니 자료가 많은 쪽을 고르세요. 국내 PC·콘솔 엔진 쪽을 노린다면 DirectX가 유리할 수 있습니다. Unity에서는 **셰이더(HLSL, Shader Graph)와 Frame Debugger**로 원리를 실무와 연결하세요.

**Windows 프로그래밍 (Win32) — 선택**
- 찬성: 메시지 루프, 핸들, 프로세스·스레드, DLL을 알면 **게임 루프와 엔진이 OS 위에서 어떻게 동작하는지** 이해하게 됩니다. 툴, 서버, 안티치트, 시스템 쪽 직군에서 쓸모가 있습니다.
- 회의: 데스크톱 UI는 C#(WPF, WinForms)이나 웹 기술로 넘어갔고, 모바일·크로스플랫폼 비중이 커져서 Windows에 국한된 지식의 가치는 예전보다 낮습니다.
- 권장: **창 하나 띄우고 메시지 루프 돌리기** 수준이면 충분합니다(DirectX 실습을 하면 자연스럽게 경험합니다). API 자체보다 **OS 개념(메모리, 스레드, 동기화, 파일 입출력)**이 더 오래 쓰입니다.

**목표 직군별 추천**

| 목표 직군 | 게임 수학 | 그래픽스 API | Win32 |
|---|---|---|---|
| Unity 클라이언트 | 깊게 | 기본 + 셰이더 | 생략 가능 |
| 엔진·그래픽스 | 매우 깊게 | **깊게** (DX12/Vulkan) | 기본 |
| 툴·시스템 개발 | 기본 | 선택 | **중간** (+ C# 툴) |
| 게임 서버 | 기본 | 생략 가능 | OS·네트워크 중심 |

**AI 시대 관점**
- AI는 OpenGL이나 DirectX 초기화 같은 **보일러플레이트는 잘 만들어 줍니다.** 반면 "왜 화면이 검게 나오는가"처럼 파이프라인 전체를 봐야 하는 디버깅에는 약합니다.
- 이제는 **API 호출을 외우기보다 원리를 이해하는 것**이 핵심입니다. 초기화 코드는 AI에게 맡기고, 각 단계의 역할을 설명할 수 있으면 됩니다.

**추천 학습 순서**
1. **게임 수학 기초:** LÖVE2D나 C++로 직접 구현
2. **OpenGL 또는 DX11 미니 렌더러:** 창 띄우기(Win32 기초 포함) → 삼각형 → 텍스처 → 카메라
3. **Unity 셰이더와 Frame Debugger로 연결:** 원리와 실무 잇기
4. 목표 직군이 정해지면 **심화:** DX12나 Vulkan, 엔진 구조, 툴 개발 등

> 💡 이렇게 만든 **작은 C++ 렌더러**는 아래 포트폴리오의 "기반" 칸에 딱 맞는 결과물입니다.

## 부록: 개발자가 아닌 가족·친구에게 — 일반인이 단련할 분야

개발자는 AI를 **만들고 다루는** 쪽이라면, 일반인은 AI를 **잘 쓰면서도 휘둘리지 않는** 쪽이 핵심입니다. 이 부록은 주변 사람에게 그대로 공유해도 됩니다.

### 1. AI 리터러시 — 기본 사용법
- **질문하는 법:** 내 상황, 원하는 것, 조건을 구체적으로 말하기 (사실상 글쓰기 능력)
- **한계 알기:** AI는 그럴듯한 거짓말(환각)을 합니다. 숫자, 법률, 의료, 최신 정보는 반드시 확인하세요.
- **작게 시작하기:** 요약, 초안 작성, 번역, 일정 정리처럼 반복되는 일 하나부터 AI에 맡겨 보세요.

### 2. 판단력과 비판적 사고 — 가장 중요
- **출처 확인 습관:** "누가, 언제, 무엇을 근거로 말했나?"
- **가짜 구분하기:** 딥페이크 영상과 음성, AI가 쓴 가짜 뉴스와 리뷰가 크게 늘었습니다.
- **판단을 맡기지 않기:** AI가 추천해도 결정과 책임은 내 몫입니다.

### 3. 안전과 보안 — 당장 필요
- **AI 기반 사기 주의:** 가족 목소리를 흉내 낸 보이스피싱, 정교한 피싱 문자와 메일. 가족끼리 확인용 암호를 정해 두는 것도 방법입니다.
- **개인정보 보호:** 주민번호, 계좌, 회사 기밀, 건강 정보는 AI에 입력하지 않기
- **디지털 취약 계층 돕기:** 부모와 조부모 세대가 가장 큰 피해를 봅니다.

### 4. 기초 소양 — 여전히 중요
- **글쓰기와 말하기:** AI에게 지시할 때도, 사람을 설득할 때도 필요합니다.
- **기초 수리와 통계 감각:** "확률 90%", "평균 대비 2배" 같은 말을 해석하는 능력은 숫자로 속이는 정보를 걸러 줍니다.
- **영어 읽기:** 번역기가 있어도 원문을 대략 확인할 수 있으면 오역에 덜 속습니다.

### 5. AI로 대체하기 어려운 능력 — 직업적 가치
- **전문 분야의 깊이:** "내 분야 + AI 활용"을 갖춘 사람이 유리합니다.
- **사람을 대하는 능력:** 공감, 돌봄, 협상, 리더십, 신뢰 관계
- **몸을 쓰는 기술:** 현장 기술, 수리, 요리, 운동, 공예 등
- **책임지는 역할:** 최종 판단과 서명이 필요한 일

### 6. 마음과 생활 — 간과하기 쉬움
- **집중력 지키기:** 짧은 영상, 무한 스크롤, 끝없는 추천에 시간을 빼앗기지 않기
- **변화에 대한 태도:** 불안이나 외면 대신 "조금씩 써 보는" 호기심
- **평생 학습:** 배우는 습관 자체가 자산입니다.
- **사람과의 관계:** AI와의 대화가 늘수록 진짜 관계의 가치는 커집니다.

### 대상별 우선순위

| 대상 | 먼저 할 것 |
|---|---|
| 직장인 | 내 업무에 AI 적용하기 + 전문성 깊이기 |
| 학생 | 기초 소양(읽기, 쓰기, 수학) + AI를 튜터로 쓰기 |
| 부모 | 아이의 AI 사용 지도 + 비판적 사고 함께 기르기 |
| 중장년·노년 | 사기 예방 + 생활 편의 기능부터 천천히 |

### 개발자와 일반인의 공통점
결국 **"AI가 해 준 것을 판단할 수 있는 힘"**이 핵심입니다. 개발자에게는 코드 검증, 일반인에게는 정보 검증이라는 차이만 있습니다. 그래서 **글쓰기(생각 정리)**와 **기초 수리(근거 판단)**는 누구에게나 시간을 들일 가치가 있습니다.

> 💡 한 줄 조언: **"AI를 매일 조금씩 쓰되, 중요한 결정은 한 번 더 의심하자."**
