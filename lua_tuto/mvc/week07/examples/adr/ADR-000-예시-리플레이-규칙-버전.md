# ADR-000 (예시): 저장된 리플레이는 "시드 + 스텝별 입력 + 규칙 버전"으로 남기고, 버전이 다르면 재생을 거부한다

- **상태:** 채택
- **날짜:** 7주차
- **작성자:** 강의 예시 (학생 ADR-001 은 다른 주제로 쓴다)

## 1. 맥락
- 6주차에 리플레이를 붙였다. 기록 = 시드 + 고정 스텝마다의 입력. Model 이 결정적이라 이것만으로 같은 판이 나온다.
- 7주차에 기록을 **파일로 저장**하게 되자 새 문제가 생겼다: 저장한 뒤 게임 규칙이 바뀌면(콤보 추가 → 점수 → 보스 등장 시점), 옛 기록을 새 규칙으로 돌려도 에러 없이 **다른 판**이 나온다.
  - 실측: 콤보 추가 후 같은 시드·입력에서 **69~71번째 스텝(약 1.1초)** 에 이미 달라졌다 (`equivalence_test`).
- 제약: Model 은 love·파일을 모른다. 기록은 작아야 한다(스텝당 1줄, 20초 ≈ 4.8KB).

## 2. 선택지
| 선택지 | 장점 | 단점 | 비용 |
|--------|------|------|------|
| A. 입력만 저장 (6주차 그대로) | 가장 단순 | 규칙이 바뀌면 **조용히 틀린** 리플레이 | 0 |
| B. 입력 + 규칙 버전, 다르면 거부 | 틀린 재생을 막는다. 기록 크기 그대로 | 규칙을 바꿀 때마다 옛 기록을 못 본다. 버전 올리는 걸 잊을 수 있다 | 작음 (헤더 1줄 + 비교 1줄) |
| C. 버전별 옛 규칙을 보관해 재생 | 옛 기록도 계속 재생 | Model 을 버전마다 보관·로드해야 함. 코드가 두 배로 늘어난다 | 큼 |
| D. 매 스텝 상태 스냅샷 저장 | 규칙과 무관하게 재생 | 크기가 수백 배, Model 구조가 바뀌면 그것도 깨진다 | 중간 |

## 3. 결정
**B.** 이 과정의 게임에서 옛 리플레이를 계속 보는 가치(C)는 그 비용보다 작다. A 는 "틀린 것을 맞는 것처럼" 보여 주므로 받아들일 수 없다. B 는 틀릴 바에는 **거부**한다.

## 4. 결과
- **좋아지는 것:** 규칙이 바뀐 뒤의 옛 기록은 "VERSION MISMATCH" 로 거부된다. 6주차 형식(버전 줄 없음)은 v1 로 읽는다.
- **감수하는 것:** 규칙을 바꿀 때마다 저장된 리플레이를 버린다. 개발자가 버전을 올리는 것을 **잊을 수 있다** → 아래 검증으로 막는다.
- **바뀐 파일:** `GameModel.RULES_VERSION`, `InputRecorder`(헤더·parse), `ReplayScene`(거부), `ReplayView`(안내). Model 규칙 코드는 0줄.

## 5. 검증
- `equivalence_test`: 버전이 1이면 6주차와 **매 스텝 같아야** 하고, 1보다 크면 **실제로 달라야** 한다. → "바꿨는데 안 올림"과 "안 바꿨는데 올림" 둘 다 잡는다.
  - 확인: 콤보를 넣고 버전을 그대로 두면 8개 중 8개 실패.
- `replay_test`: 버전이 다른 기록은 진행하지 않고 안내를 그린다. 헤더가 저장·복원된다. 깨진 파일은 nil + 이유.

## 6. 다시 볼 조건
- 저장한 리플레이를 **공유**(랭킹·대회)하게 되면 → C 를 다시 검토한다(옛 리플레이 검증이 필요해진다).
- 버전이 자주 올라 사용자가 불편해하면 → 규칙과 무관한 변경(연출·View)은 버전을 올리지 않는다는 원칙을 문서로 더 분명히 한다.
