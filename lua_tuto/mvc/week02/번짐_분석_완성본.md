# 모놀리식 "번짐(Ripple)" 분석 — 겔러그 완성본

> **대상:** `galaga_monolith` (기본판) → `galaga_monolith_full` (유도 미사일 + 보스 탄막 추가)
> **목적:** 기능 2개를 끼워 넣을 때 수정이 **파일 전역으로 번지는 현상**을 수치와 위치로 공유한다.
> **결론 한 줄:** **기능은 2개인데, 수정은 파일 전체 23개 블록에 흩어졌다.** 책임이 섞여 있기 때문이다.

---

## 1. 정량 요약 (diff 근거)

| 지표 | 값 | 산출 방법 |
|------|----|-----------|
| 기본판 줄 수 | **280** | `wc -l galaga_monolith/main.lua` |
| 완성본 줄 수 | **418** | `wc -l galaga_monolith_full/main.lua` |
| 순증가 | **+138줄** (+49%) | 418 − 280 |
| 추가/변경 라인(`>`) | **176** | `diff ... \| grep -c '^>'` |
| 원본에서 바뀐 라인(`<`) | **38** | `diff ... \| grep -c '^<'` |
| **흩어진 변경 블록(hunk)** | **23곳** | `diff ... \| grep -E '^[0-9]'` |

> 재현:
> ```sh
> cd lua_tuto/mvc/week02/examples
> diff galaga_monolith/main.lua galaga_monolith_full/main.lua
> ```

**핵심:** "기능 2개 추가"가 **23개 지점**을 건드렸다. 변경이 한 곳에 모이지 않고 **상수 → 상태 → 입력 → 이동 → 충돌 → 그리기 → 상태전이**까지 전 구간에 퍼졌다.

## 2. 기능별 번짐 지도

### 🟢 유도 미사일 `[H1~H4]` — 약 6개 지점

| # | 번진 곳 | 무엇을 건드렸나 | 왜 번졌나(원인) |
|---|---------|----------------|-----------------|
| H1 | 상수 영역 | `HOMING_SPEED`, `HOMING_TURN` 추가 | 설정이 코드에 흩어짐 |
| H2 | 총알 자료구조 | 모든 총알에 `vx/vy/homing` 필드 추가 | 데이터 모양이 바뀌니 **생성하는 모든 곳**이 영향 |
| H2 | 발사 입력 | `X` 키 + `missileCd` 쿨다운 신설 | 입력 해석과 생성이 한 덩어리 |
| H3 | 총알 이동 루프 | 유도 분기(목표 추적·선회·정규화) 삽입 | 이동 로직에 조건문이 끼어 복잡도↑ |
| H3 | 신규 함수 | `nearestTarget()` 추가 | 로직 파일이 더 길어짐 |
| H4 | 그리기 | 미사일 색상 분기 | **표현(View)**도 같이 수정 |

> 아픈 지점: **총알 자료구조 하나 바꿨더니** 일반 총알 생성부·이동부·그리기까지 전부 손봐야 했다.

### 🟣 보스 탄막 `[B1~B9]` — 약 9개 지점

| # | 번진 곳 | 무엇을 건드렸나 | 왜 번졌나(원인) |
|---|---------|----------------|-----------------|
| B1 | 상태/상수 | `boss`, `bossSpawned`, `won`, 보스 상수들 추가 | 전역 상태 덩어리가 더 커짐 |
| B2 | `resetGame` | 신규 상태 초기화 추가 | 상태가 늘면 **초기화도 매번** 따라감 |
| B3 | 등장 조건·전멸 로직 | 점수 도달 시 `spawnBoss`, 전멸 분기 수정 | 상태 전이가 여러 곳에 흩어짐 |
| B4 | 보스 이동 | 좌우 이동·반사 코드 신설 | update가 또 길어짐 |
| B5 | 적 총알 자료구조 | 적 총알에 `vx` 추가(방사탄과 통일) | **무관한 일반 적 총알 생성부**까지 수정 |
| B5 | 보스 발사 | 원형 18발 방사 패턴 생성 | 발사 로직 추가 |
| B6 | 적 총알 이동 루프 | `vx` 적용 + 좌우 화면밖 제거로 변경 | 데이터 모양 변경이 이동부로 전파 |
| B7 | 충돌 | 플레이어 총알 × 보스(HP 다중 피격) 신설 | 충돌 종류가 늘면 루프도 늘어남 |
| B8 | 그리기 | 보스 사각형 + HP 바 | 표현(View) 또 수정 |
| B9 | 그리기/상태 | 승리 메시지 분기(`won`) | 상태 전이가 렌더까지 번짐 |

> 아픈 지점: 보스의 **원형 탄막**을 만들려고 `vx`를 추가했더니, 보스와 전혀 상관없는 **일반 적 총알 생성·이동 코드**까지 바뀌었다.

## 3. "왜" 번졌는가 — 근본 원인 3가지

1. **책임 미분리 (Model+View+Controller 혼재)**
   하나의 `update`가 입력·물리·충돌·연출을 모두 한다. 새 기능은 이 모든 축을 동시에 건드릴 수밖에 없다.

2. **데이터와 로직의 강결합**
   총알/적 총알의 **자료구조**가 바뀌면, 그걸 **만들고·움직이고·그리는** 모든 코드가 연쇄로 바뀐다. 경계(인터페이스)가 없어서다.

3. **상태 전역 덩어리**
   `boss`, `won` 같은 상태를 추가할 때마다 선언·`resetGame`·등장조건·그리기에 **중복 반영**해야 한다.

## 4. 이걸 MVC가 어떻게 줄이는가 (3~4주차 예고)

| 번짐의 원인 | MVC 전환 후 |
|-------------|-------------|
| 총알 자료구조 변경이 생성·이동·그리기로 전파 | `BulletModel`이 데이터·이동을 캡슐화 → **생성/이동은 Model 한 곳**, 그리기는 `BulletView` 한 곳 |
| 충돌 로직에 연출·사운드가 박힘 | 충돌은 Model에서 판정만, "죽음"을 **이벤트로 발행** → View가 파티클/사운드 담당 |
| 입력과 발사 생성이 엉킴 | `InputManager`/`Controller`가 입력만 해석 → Model에 "쏴" 명령 |
| 창 없이 테스트 불가 | Model에 `love.*`가 없으니 **헤드리스로 "보스 HP·점수 계산" 단위 테스트** 가능 |

> 같은 "보스 추가"라도 MVC에서는 **BossModel(로직) / BossView(표현) / 입력 바인딩**으로 수정 위치가 **예측 가능하게 격리**된다. "어디를 고칠지"가 명확해지는 것이 핵심 이득이다.

## 5. 수업에서의 사용법

- **강사:** 이 문서 + `galaga_monolith_full`로 "기능 2개 = 수정 23곳"을 시연한다.

### 부록 — 변경 블록 분포 (hunk)
`diff`가 보고한 변경 블록 23개는 파일의 **앞(상수·상태) → 중간(update 전체) → 뒤(draw)** 에 고르게 퍼져 있다.
한 기능이 한 곳에 모이지 않는다는 것이 모놀리식의 본질적 비용이다.
