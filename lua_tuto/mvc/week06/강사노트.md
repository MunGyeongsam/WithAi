## 2. 시간이 밀릴 때 줄이는 순서
1. 실습 2 → 완성본 복사 허용 (Dispatcher 루프 4줄, record·replay 각 3~4줄).
2. 7절 비교 토론 → 표만 보여 주고 메모는 숙제.
3. 선택 과제(pause Action, 한 칸씩 앞/뒤) → 숙제.
- **줄이면 안 되는 것:** 리듀서 순수성(실습 1), 재사용 테이블 함정(5-3), 6절 `[한계, 그대로]`.

## 3. 시연: 비순수 리듀서가 시간 여행을 깨뜨리는 장면 (5분)
완성본 `turn` 을 `state.nextDir = dir; return state` 로 바꾸고 `reducer_test` → 순수성 테스트가 실패하고, `flux_test` "옛 상태는 그대로 남아 있다" 가 실패하는 것을 보여 준다. 되돌린 뒤 "같은 테이블을 돌려주는 게 **변화 없음**의 신호인데, 제자리 수정하면 **변화가 있어도** 같은 테이블이라 Store 구독자가 못 알아챈다" 까지 연결.

## 4. 재사용 테이블 함정 운영 팁
- 학생에게 `self.steps[#self.steps + 1] = input` 을 먼저 쓰게 하고 `replay_test` 를 돌리게 한다. "기록은 입력의 복사본이다" 와 재현 테스트 3개가 실패한다.
- 이때 **게임을 실행하면 아무 이상이 없다**는 걸 직접 보게 한다. 리플레이를 켜야 이상해진다. "증상과 원인이 멀리 떨어진 버그"의 실물이다.
- 4주차 README 1-4 에 이미 "보관하면 안 된다, 6주차에서 중요해진다"고 써 두었다. 미리 경고해도 빠진다는 게 포인트.

## 5. 예상 질문
| 질문 | 답의 방향 |
|------|----------|
| "매번 새 테이블이면 느리지 않나요?" | Snake 는 tick 당 테이블 몇 개라 무시 가능. 겔러그 전체를 이렇게 하면 프레임당 수백 개 → 7주차 프로파일링 주제. **어디에 Flux 를 쓸지**는 규모로 판단(README 7절 마지막 행). |
| "Redux 랑 같은 건가요?" | Redux 는 Flux 의 변형(Store 1개, 리듀서). 오늘 만든 건 Redux 쪽에 가깝다. Dispatcher 가 따로 있는 건 원래 Flux 모양. |
| "turn 이 1200개나 기록되는 건 버그 아닌가요?" | 봇이 매 프레임 누르기 때문. 결과는 같다. 줄이려면 Controller 가 `state.nextDir` 와 같으면 안 보내면 되지만, 그러면 Controller 가 규칙(반대 방향 등)을 일부 알게 된다. **기록 크기 vs 규칙 위치**의 트레이드오프. |
| "겔러그도 리듀서로 바꿔야 하나요?" | 바꿀 필요 없다. 이미 "시드 + 스텝 입력"이 Action 열 역할을 한다. 대신 시간 여행(n번째 시점)은 처음부터 다시 돌려야 한다. |
| "리플레이가 있으면 4주차 `[한계]` 는 해결된 거 아닌가요?" | 아니다 — 6절. 기록은 **일어난 판**을 재현할 뿐, 실시간 입력이 프레임 경계에서 양자화되는 건 그대로. 이걸 헷갈리면 퀴즈 7번에서 감점. |
| "네트워크 대전도 이걸로 되나요?" | 원리는 같다(lockstep: 입력만 주고받음). 다만 "몇 번째 스텝의 입력인가"를 양쪽이 합의해야 하고 지연 처리가 필요하다. 범위 밖. |

## 6. 개념 퀴즈 정답 & 채점 포인트 (README 10절)

**1.** 한 가지: Action 을 dispatch. 얻는 것: ① 모든 변경이 한 곳을 지나므로 **기록·검증**이 저절로 됨 ② 변경 원인을 Action 목록으로 **추적·재생** 가능.

**2.** 제자리 수정하면 보관한 "옛 state" 가 같은 테이블이라 함께 바뀐다 → 과거가 사라진다. `reducer_test` 순수성(스냅샷 비교), `flux_test` "옛 상태는 그대로" 에서 실패.

**3.** 리듀서가 **어떤 테이블도 만든 뒤 고치지 않는다**. 공유 대상이 바뀌지 않으니 공유해도 관찰 결과가 같다. ❌ 감점: "얕은 복사라서 안전" — 얕은 복사 자체는 안전의 이유가 아니다.

**4.** 리듀서는 실시간을 모르고 tick 의 **개수와 순서**만 본다. 재생 속도는 Action 을 언제 넣느냐일 뿐, 순서는 같다.

**5.** 기록 줄 수 = 프레임 수 ≠ 스텝 수. 20fps 면 프레임당 3스텝인데 1줄만 남아 재생 시 1/3 길이가 되고(또는 입력이 어긋나) 다른 판이 된다.

**6.** 게임은 매 스텝 `read()` 직후 그 테이블을 바로 쓰고 끝난다. 값이 다음 프레임에 덮어써져도 이미 쓴 뒤다. 기록만 **나중에** 읽기 때문에 그때 드러난다.

**7.** 기록은 이미 일어난 Action 열을 재현할 뿐이고, 실시간 키가 어느 tick/스텝에 들어가는지는 여전히 fps 에 좌우되기 때문.

**8.** 봇은 **상태**를 보고 누른다 → 같은 state 에서 같은 키 → tick 열이 같다. 사람(시각 기반)은 "언제" 누르느냐가 프레임 경계에 따라 다른 tick 에 걸린다.

**9.** 문자열 패턴이라 `local st = state; st["score"] = 0` 같은 우회를 못 잡는다. 보완: 실행 중 검사(키를 누른 뒤 이전 state 스냅샷 비교, `flux_test`).

**10.** ① 시드 주입(3주차) ② 고정 스텝 + 스텝마다 `input` 하나로 Model 을 부름(3~4주차) ③ `ctx.scenes` 레지스트리로 새 씬을 main 1줄로 추가(5주차). (Controller·Model 분리를 넣어도 정답 인정.)

## 7. 자주 막히는 곳
- **`tick` 에서 `s.snake` 를 만들고 `state.snake` 에 대입**: 순수성 실패. 메시지에 `snake` 경로가 나오면 이것.
- **충돌 검사 범위를 `#body` 전체로**: "꼬리가 있던 칸으로는 들어갈 수 있다" 실패.
- **`placeFood` 반환값 하나만 받음**: `s.food = placeFood(...)` → rng 가 안 바뀜.
- **`ActionLog:replay` 에서 `n` 이 `#entries` 보다 클 때**: `math.min` 을 빠뜨리면 nil action → 에러.
- **`ReplayScene:update` 에서 `done()` 검사 누락**: `steps[cursor]` 가 nil → Model 이 nil input 으로 에러.
- **4배속을 `dt * speed` 로 Model 에 넘김**: 재현 테스트 speed 4 만 실패한다. README 5-5 로 연결.

## 8. 실행 확인 기록 (작성자 검증)
- 실제 LÖVE 11.5(macOS), 각 앱 1회, 임시 복사본·고유 폴더·하드 타임아웃 20~25초, 결과는 파일로 기록.
  - **Snake:** 20프레임째 ↑ 입력 → 155프레임에 사망(ticks 11) → V → 192프레임에 리플레이 종료. 실시간·리플레이 최종 상태 일치(ticks 11, 머리 (11,1)). 오류 없음.
  - **겔러그:** Enter → 플레이 → 게임오버 → 결과 화면 → V → 리플레이 종료(120프레임). 기록 29스텝 = 재생 29스텝, 플레이어 x 일치. 오류 없음.
  - **Snake (2차, dt 상한 추가 후):** 같은 절차로 다시 1회. 191프레임에 리플레이 종료, 실시간·리플레이 일치(ticks 11, 머리 (11,1)). 오류 없음.
- 검증 스크립트가 게임오버를 빨리 만들려고 상태를 직접 바꿨다. 이 실행의 목적은 **런타임 연결 확인**뿐이고, 동작 검증은 테스트가 맡는다.

### 9-1. 재검토(2차)에서 고친 것 — 변이를 넣어 "못 잡는 것"을 찾음
| 변이 | 초판 | 지금 |
|------|------|------|
| 왼·위·아래 벽 검사 삭제, 오른벽 `>=` | **전 테스트 통과** (벽 테스트가 오른쪽 하나, 봇은 벽을 피함) | 네 벽 + 끝 칸 짝 테스트 → 각각 1개 실패 |
| `restart` 가 시드 무시 | **전 테스트 통과** (실시간·리플레이가 같은 리듀서라 함께 틀림) | `reducer_test` restart 시드 테스트 |
| 겔러그 기록기가 `ctx.seed()` 를 따로 호출 | **전 테스트 통과** (가짜 seed 가 상수) | 가짜 seed 도 호출마다 다른 값 → `replay_test` 7개 실패 |
| Dispatcher tap/Store 순서 뒤바꿈 | **통과** (README 는 "순서 중요"라고 주장) | "리듀서 에러에도 기록은 남는다" 테스트 |
| 겔러그 씬에서 `love`, Model 에서 `math.random` | 6주차 `layer_check` 가 Snake 전용 | `layer_check galaga_replay` |

- **동작 수정 2건.** ① Snake `App:update` 에 프레임 dt 상한 0.25초(겔러그와 같음). 없으면 창을 끌어 2초 멈췄다 오면 tick 16개가 한 프레임에 몰려 조작 기회 없이 죽는다. 테스트 추가. ② 시드 직렬화 `%d` → `%.0f`. `newSeed` 값(약 1.8×10¹²)은 32비트를 넘는데, Windows 용 Lua 5.1 은 `%d` 를 32비트 `long` 으로 처리해 값이 깨진다(macOS 에서는 안 드러남, Windows 실기 미확인). LuaJIT 는 문제없지만 학생이 테스트를 lua5.1 로 돌릴 수 있다.
- **고치지 않고 둔 것 (질문 대비).**
  - `tick` 의 충돌 범위 `#body - (eats and 0 or 1)`: 먹을 때는 그 칸이 먹이(빈 칸)라 몸과 겹칠 수 없으므로 실제로는 항상 `#body - 1` 과 같다. 테스트가 먹이를 몸 위에 둔 인공 상태를 만들 수 있어 방어적으로 두었다. 학생이 "왜 eats 를 보나요?"라고 물으면 좋은 관찰이다.
  - `InputRecorder` 는 스텝마다 새 테이블(초당 60개)을 만든다. 4주차가 GC 때문에 입력 테이블을 재사용한 것과 어긋난다는 질문이 나오면: 기록은 **보관이 목적**이라 복사가 필수다. 크기가 문제면 스텝을 문자열/숫자 하나로 팩킹하면 된다(7주차 프로파일링 거리).
  - Snake `Ticker.acc` 는 새 판에서 초기화되지 않는다 → 첫 tick 까지의 시간이 판마다 0~0.12초 다르다. tick 은 Action 으로 기록되므로 리플레이에는 영향이 없다.
