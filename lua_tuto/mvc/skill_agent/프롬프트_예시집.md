## 1. 설계 — 적 AI 구조 잡기

**❌ 나쁜 예**
```
갤러그 적 AI 설계해줘
```

**문제:** 맥락(어디까지 했나), 범위(적 몇 종, 어떤 행동), 제약(MVC), 출력 형식이 없다. AI 는 일반적인 갤러그 설계를 길게 쓰고, 코드까지 쏟아낸다.

**✅ 좋은 예**
```
[맥락] week04 갤러그 MVC 를 이어서 만든다. 지금 적은 편대로만 움직이고 AI 가 없다.
[목표] 적 2종(돌진형, 저격형)의 AI 구조를 설계한다. 코드는 아직 쓰지 않는다.
[참조] models/GameModel.lua, models/EnemyModel.lua (둘 다 읽기 전용)
[제약] AI 로직은 models/ 에만 둔다. love.* 금지. 같은 시드와 입력이면 결과가 같아야 한다.
[출력 형식]
1) 적 종류별 행동 설명 표 (상태, 전이 조건)
2) 새로 만들 파일과 고칠 파일 목록 (각 1줄 이유)
3) GameModel 과 주고받을 데이터 (함수 시그니처만)
[검증] 이 설계로 어떤 헤드리스 테스트를 쓸 수 있는지 3개 제안
모호한 점이 있으면 설계 전에 질문부터 해.
```

**포인트:** "코드는 아직 쓰지 않는다" + "질문부터". 설계 단계에서 틀린 걸 잡는 게 가장 싸다.

## 2. 패턴 선택 — State vs Strategy

**❌ 나쁜 예**
```
적 AI에 무슨 디자인 패턴 써야 돼?
```

**문제:** 어떤 행동을 원하는지 없다. AI 는 패턴 목록을 나열하거나, 하나를 근거 없이 고른다.

**✅ 좋은 예**
```
[맥락] 돌진형 적은 대기 → 추적 → 돌진 → 복귀 순서로 움직인다.
저격형 적은 제자리에서 플레이어를 조준해 쏘는데, 조준 방식을 "직선 조준"과 "예측 조준" 중에서 바꾸고 싶다.
[목표] 두 적에 각각 맞는 패턴을 고른다.
[제약] 수업에서 배운 패턴(State, Strategy, Observer, Factory Method) 중에서 고른다.
[출력 형식]
1) 적별 후보 패턴 2개 비교표 (장점, 단점, 우리 코드에서 바뀌는 곳)
2) 추천과 근거 3줄
3) 골격만 (TODO 포함 20줄 이내). 완성 코드는 쓰지 마.
[검증] 추천한 구조가 맞는지 확인할 질문 1개를 나에게 던져.
```

**포인트:** "상태가 바뀌는 행동"(돌진형 → State)과 "갈아끼우는 알고리즘"(조준 → Strategy)을 **증상으로 설명**하면 AI 가 정확히 고른다. 보고서의 "패턴 적용 표 — 왜 썼는지"에 그대로 쓸 수 있다.

## 3. 구현 — FSM 상태 1개 추가

**❌ 나쁜 예**
```
적 AI 전부 구현해줘. 추적, 공격, 도주, 복귀 다 넣고 보스도.
```

**문제:** 목표가 5개 이상이다. 한 번에 수백 줄이 나오고, 어디가 틀렸는지 찾을 수 없다. 로그에도 "전부 만들어 줌" 한 줄밖에 못 쓴다.

**✅ 좋은 예**
```
[맥락] models/enemy_states.lua 에 idle 상태만 있다 (State 패턴, 상태마다 { enter, update } 테이블).
[목표] chase 상태 1개만 추가한다. idle 에서 플레이어와 거리 150 이하면 chase 로 전이.
[참조] models/enemy_states.lua (수정), models/EnemyModel.lua (읽기 전용)
[제약] Lua 5.1, 모든 변수 local, love.* 금지, 기존 idle 코드는 건드리지 마.
[출력 형식] 바뀐 부분만 보여 주고, 각 변경에 한 줄 설명.
[검증] 이 변경을 확인할 테스트 이름 2개만 제안 (코드는 다음 요청에서).
```

**포인트:** **한 번에 상태 1개.** 다음 상태는 테스트가 통과한 뒤 새 요청으로.

## 4. 테스트 먼저

**❌ 나쁜 예**
```
테스트 코드도 짜줘
```

**문제:** 무엇을 검증할지, 어떤 러너를 쓸지, 창 없이 돌아야 하는지 모른다. AI 가 `love.load` 안에서 도는 테스트를 만들거나 외부 라이브러리(busted 등)를 쓰기도 한다.

**✅ 좋은 예**
```
[맥락] 헤드리스 테스트는 tests/helper.lua 의 helper.test(name, fn) 을 쓴다. fn 은 통과 시 true 를 반환해야 한다.
[목표] chase 전이 규칙의 테스트를 구현 "전에" 작성한다.
[참조] tests/helper.lua (읽기 전용, 사용법 참고), models/enemy_states.lua (읽기 전용)
[제약] luajit 으로 창 없이 실행. love 사용 금지. 외부 라이브러리 금지. dt = 1/60 고정.
[출력 형식]
1) 검증 목록 표 (테스트 이름 | 준비 | 행동 | 기대) — 정상, 경계값(정확히 150), 실패 경우 포함
2) tests/enemy_fsm_test.lua 전체
3) 실행 명령과 "지금은 실패가 정상"인 테스트 표시
[검증] 기대값을 구현에 맞춰 바꾸지 마.
```

**포인트:** **경계값(정확히 150)** 을 명시하면 `<` 와 `<=` 실수를 테스트가 잡는다.

## 5. Lua 문법 — 웨이브 문자열 파서 (게임시스템설계)

**❌ 나쁜 예**
```
"A3 B2 C1" 같은 문자열 파싱하는 함수 만들어줘
```

**문제:** 결과 형태, 잘못된 입력 처리, 사용할 Lua 기능이 없다. AI 가 `string.split`(Lua 에 없음) 같은 다른 언어 습관을 쓰기도 한다.

**✅ 좋은 예**
```
[맥락] 웨이브 데이터를 문자열로 정의한다. "A3 B2 C1" = A형 3마리, B형 2마리, C형 1마리.
[목표] models/wave_parser.lua 에 parse(str) 함수를 만든다.
[제약]
- Lua 5.1 표준 라이브러리만 (string.gmatch, string.match, tonumber). string.split 같은 없는 함수 금지.
- 잘못된 토큰("B", "x", "A0")이 있으면 조용히 건너뛰지 말고 error("잘못된 토큰: B") 로 알린다.
- 모듈은 local M = {} ... return M 형태.
[출력 형식]
1) 반환 형태 예: { { kind = "A", count = 3 }, ... }
2) 코드 + 사용한 Lua 문법(패턴 %a %d+, 캡처, tonumber) 설명 3줄
[검증] 정상 1개, 빈 문자열 1개, 잘못된 토큰 1개를 pcall 로 확인하는 테스트
```

**포인트:** `("A3 B C1"):gmatch("(%a)(%d+)")` 는 `"B"` 를 **에러 없이 건너뛴다.** 이 함정을 프롬프트에서 미리 막았다. 보고서의 "Lua 문법 사용처 표"에 `gmatch`, 패턴 캡처, `pcall` 이 들어간다.

## 6. Lua 문법 — 메타테이블과 클래스 상속 (게임시스템설계)

**❌ 나쁜 예**
```
적 클래스 상속 구조 만들어줘
```

**문제:** AI 가 다른 언어식 `class` 키워드나 외부 OOP 라이브러리(middleclass 등)를 쓰거나, 우리 `class.lua` 와 다른 방식으로 만든다.

**✅ 좋은 예**
```
[맥락] models/class.lua 는 class(base) 로 클래스를 만들고, 인스턴스는 Class(...) 로 생성하며 init 을 호출한다.
[목표] Enemy 를 부모로, Rusher(돌진형)와 Sniper(저격형) 자식 클래스를 만든다. 공통 takeDamage 는 부모에, update 는 자식마다 다르게.
[참조] models/class.lua (읽기 전용), models/EnemyModel.lua (부모로 사용)
[제약] 외부 라이브러리 금지. setmetatable / __index 기반인 class.lua 만 쓴다. 메서드는 콜론(:) 정의.
[출력 형식]
1) 자식 클래스 코드
2) Rusher 인스턴스에서 takeDamage 를 찾을 때 __index 를 따라가는 순서를 화살표로 설명
[검증] 자식 인스턴스가 부모 메서드를 쓰는지, update 가 자식 것으로 바뀌는지 테스트 2개
```

**포인트:** "`__index` 탐색 순서를 설명하라"를 넣으면, 학생이 **자기 코드를 말로 설명할 수 있게** 된다 (시연·구술 대비).

## 7. 디버깅 — 에러 전달

**❌ 나쁜 예**
```
에러 나요 고쳐주세요
```

**문제:** 에러 메시지도 코드도 없다. AI 는 추측으로 흔한 원인 5개를 나열한다.

**✅ 좋은 예**
```
[실행 결과]
luajit: models/enemy_states.lua:14: attempt to index local 'world' (a nil value)
stack traceback:
  models/enemy_states.lua:14: in function 'update'
  models/EnemyModel.lua:31: in function 'update'
  tests/enemy_fsm_test.lua:9: in function <tests/enemy_fsm_test.lua:7>
[관련 코드] (enemy_states.lua 10~18줄, EnemyModel.lua 28~33줄 붙여넣기)
[시도한 것] world 가 nil 인지 print 로 확인 → nil 맞음. 어디서 안 넘어오는지 모르겠음.
[질문] 원인을 먼저 설명하고, 수정은 최소한으로. 다른 함수는 건드리지 마.
```

**포인트:** **스택 트레이스 전문 + 시도한 것.** 이번 에러는 호출 체인(테스트 → EnemyModel → states)에서 인자가 빠진 것이라, 트레이스가 없으면 찾기 어렵다.

## 8. 리팩터링 — MVC 경계 위반 고치기 (게임인공지능)

**❌ 나쁜 예**
```
코드 깔끔하게 정리해줘
```

**문제:** "깔끔"의 기준이 없다. AI 가 이름을 바꾸고 파일을 합치고 동작까지 바꿀 수 있다.

**✅ 좋은 예**
```
[맥락] tests/layer_check.lua 를 돌렸더니 아래 위반이 나왔다.
FAIL  models/EnemyModel.lua:42  [love]  love.graphics.setColor(1, 0, 0)
[목표] 이 위반 1건만 고친다. 피격 시 빨간색으로 그리는 기능은 유지한다.
[참조] models/EnemyModel.lua (수정), views/EnemyView.lua (수정), models/GameModel.lua (읽기 전용)
[제약] Model 은 "맞았다"는 사실(예: hitTimer 값)만 갖고, 색은 View 가 정한다. 그 외 코드는 바꾸지 마.
[출력 형식] 파일별 바뀐 부분만 + 왜 이 계층에 두는지 한 줄씩
[검증] layer_check 통과 + 가짜 gfx 로 "맞은 적은 빨간색으로 그린다" View 테스트 1개
```

**포인트:** **도구의 출력(layer_check)을 그대로 붙이면** 목표가 정확해진다. "기능 유지"를 명시해 리팩터링이 기능 변경으로 번지지 않게 한다.

## 9. 에이전트에게 맡기기 — 수정 범위 제한 (Antigravity)

**❌ 나쁜 예**
```
보스 추가해줘
```

**문제:** 에이전트는 파일을 직접 고친다. 범위를 안 주면 GameModel, main.lua, 테스트까지 마음대로 바꾸고, 테스트를 지워서 통과시키기도 한다.

**✅ 좋은 예**
```
/start-session 으로 시작한다.

[목표] 보스 등장 조건만 구현: 3웨이브를 클리어하면 GameModel 이 "bossSpawn" 이벤트를 1회 낸다. 보스 자체 행동은 다음 세션.
[수정 허용 파일] models/GameModel.lua, tests/boss_spawn_test.lua (새 파일)
[읽기 전용] 그 외 모든 파일
[제약]
- 코드 수정 전에 planner 로 계획을 보여 주고 내 승인을 기다려라.
- 기존 테스트를 삭제하거나 기대값을 바꾸지 마라.
- 테스트 실행 외의 명령(설치, 삭제, git)은 실행하지 마라.
[검증] 끝나면 test-runner 로 전체 테스트를 돌리고, 바뀐 파일 목록과 결과를 요약해라.
```

**포인트:** **수정 허용 파일 목록**이 에이전트 프롬프트의 핵심이다. `/end-session` 이 허용 범위 밖 변경을 표시해 준다. 범위 밖 변경을 발견해 되돌렸다면 그것이 로그의 **"거절·수정 사례"**다.

## 10. 마무리 — 인계 메모와 로그

**❌ 나쁜 예**
```
오늘 한 거 정리해줘
```

**문제:** AI 가 성과 위주로 요약하고 실패와 거절을 빼며, 프롬프트 원문 대신 요약을 쓴다. 채점에 필요한 정보가 사라진다.

**✅ 좋은 예**
```
worklog-writer 스킬로 이번 세션 로그를 작성해 줘.
- 내가 보낸 프롬프트는 원문 그대로 옮겨라. 요약하지 마.
- 판정이 "수정 후 채택"이나 "거절"인 것은 문제점(파일:줄)과 다음 프롬프트에서 바꾼 점을 꼭 적어라.
- 커밋 해시: a1b2c3d (chase 상태), e4f5g6h (테스트)
- 테스트 결과: 통과 6 / 실패 0 (내가 직접 확인함)
- 내가 확인하지 않은 내용은 (확인 필요)로 남겨라.
- 마지막에 다음 세션용 인계 메모 10줄 이내.
```
