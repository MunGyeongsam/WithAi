|---|---|---|---|---|
| **규칙** | 교칙 | 항상, 또는 조건에 맞을 때 자동 | `AGENTS.md`, `.agents/rules/*.md` | 없음 (스킬로 대신) |
| **스킬** | 업무 매뉴얼 | 관련 작업일 때 AI 가 골라 읽음 | `.agents/skills/<이름>/SKILL.md` | ✅ 업로드 |

> 한 문장: **규칙은 "항상 지킬 것", 스킬은 "이럴 때 이렇게", 워크플로는 "이 순서대로", 에이전트는 "이 역할만".**
>
> ※ 워크플로 경로는 공식 문서에 명시돼 있지 않다. Customizations → Workflows 패널에 안 보이면 패널에서 새로 만들고 내용을 붙여 넣는다.

**무엇을 만들까?**

| 이런 문제가 있으면 | 만들 것 |
|---|---|
| 매번 "Lua 5.1, local 만" 을 다시 쓴다 | 규칙 (Gemini 앱이면 스킬) |
| 특정 작업마다 같은 절차를 설명한다 | 스킬 |
| 여러 단계를 늘 같은 순서로 한다 | 워크플로 |
| AI 가 계획만 세워야 하는데 자꾸 코드를 고친다 | 에이전트 (도구 제한) |

Gemini 앱만 쓰는 학생은 **스킬만** 알면 된다.

## 1. 규칙 (Rules)

### 1-1. 개념

- AI 가 **매번 자동으로** 읽는 프로젝트의 기본 약속이다. 내가 부르지 않아도 적용된다.
- 그래서 **짧고 절대적인 것**만 둔다. "Lua 5.1 만", "Model 에서 love.* 금지" 처럼.
- 절차나 긴 설명은 규칙이 아니라 스킬로 만든다. 규칙이 길면 다른 규칙과 함께 한도를 넘어 일부가 빠진다.

### 1-2. 작성 가이드

**위치**
- 프로젝트 루트 `AGENTS.md` (또는 `GEMINI.md`): 공통 규칙 5~10줄
- `.agents/rules/<이름>.md`: 조건별 규칙. **바로 아래 파일만** 읽고 하위 폴더는 무시된다.
- 전역(모든 프로젝트): `~/.gemini/AGENTS.md` 등

**형식**
```markdown
---
trigger: glob
globs: "**/models/**/*.lua"
---

- 이 폴더에서는 love, print, io 를 쓰지 않는다.
```

| `trigger` | 적용 시점 | 필요한 필드 |
|---|---|---|
| `always_on` | 항상 | — |
| `glob` | 패턴에 맞는 파일을 다룰 때 | 패턴 (`*` 로 시작하면 따옴표) |
| `model_decision` | AI 가 설명을 보고 판단 | `description` |
| `manual` | 내가 `@규칙이름` 으로 언급할 때만 | — |

**주의**
- glob 패턴 필드 이름(위 예시의 `globs`)은 버전마다 다를 수 있다. Customizations → Rules 에서 Glob 규칙을 하나 만들어 생성된 파일을 확인한다.
- 파일당 24KB, 활성 규칙 전체 약 2만 토큰 한도. 넘치면 큰 파일부터 본문 대신 경로만 전달된다.
- 명령형 한 줄 규칙으로 쓴다. 이유는 괄호로 짧게.

### 1-3. 사용 예시

**예시 1 — 프로젝트 공통 규칙 (`AGENTS.md`, 항상 적용)**
```markdown
# 갤러그 MVC 프로젝트 규칙

- LÖVE 11.5 + Lua 5.1(LuaJIT). 5.2+ 문법(//, goto, <const>) 금지.
- 모든 변수와 함수는 local. 모듈은 local M = {} ... return M.
- models/ 는 love, print, io 를 쓰지 않는다. views/ 와 controllers/ 는 주입받은 gfx, isDown 만 쓴다.
- 검증은 tests/ 의 헤드리스 테스트 우선. 게임 실행은 필요할 때 1회.
- 요청하지 않은 파일은 수정하지 않는다.
```
효과: 프롬프트마다 제약을 다시 쓰지 않아도 된다.

**예시 2 — Model 폴더 전용 규칙 (`.agents/rules/model-purity.md`, glob)**
```markdown
---
trigger: glob
globs: "**/models/**/*.lua"
---

- love, print, io, os.time, os.clock 사용 금지 (결정성과 헤드리스 테스트를 위해).
- 무작위는 models/rng.lua 의 시드 기반 Rng 만 쓴다.
- 그리기용 필드(색상, 이미지 경로)를 Model 에 두지 않는다.
```
효과: Model 파일을 다룰 때만 켜져서 다른 작업의 규칙 한도를 쓰지 않는다.

**예시 3 — 제출 직전에만 켜는 규칙 (`.agents/rules/submission-check.md`, manual)**
```markdown
---
trigger: manual
---

- 새 기능 추가 금지. 버그 수정과 문서만.
- 모든 변경 뒤 tests/ 전체와 layer_check 를 실행한다.
- README.md 의 실행·검증 방법이 실제 명령과 같은지 확인한다.
```
사용: 채팅에 `@submission-check 지금부터 제출 준비 모드` 라고 쓴다.

## 2. 스킬 (Skills)

### 2-1. 개념

- **특정 작업을 잘하는 방법**을 적어 둔 매뉴얼이다. AI 는 평소에는 이름과 설명(`description`)만 보고, 관련 작업이라고 판단하면 본문을 읽는다.
- 그래서 스킬이 많아도 평소 부담이 적다. 규칙과 달리 **길고 자세해도** 된다 (그래도 1~2쪽 권장).
- **Gemini 앱과 Antigravity 가 같은 `SKILL.md` 표준**을 쓴다. 하나 만들면 양쪽에서 쓴다.
- 여러 스킬을 **겹쳐** 쓸 수 있다 (예: `lua51-guard` + `mvc-boundary`).

### 2-2. 작성 가이드

**구조**
```
my-skill/
├── SKILL.md        # 필수
├── examples/       # 선택: 좋은 예 / 나쁜 예
└── resources/      # 선택: 체크리스트, 템플릿, 데이터
```

```markdown
---
name: my-skill
description: 무엇을 하는지 + 언제 쓰는지 (한두 문장)
---

# 목적
# 절차
# 하지 말 것
# 출력 형식
# 예시
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `name` | ✅ | 소문자, 숫자, 하이픈. **폴더 이름과 같게** |
| `description` | ✅ | AI 가 이 문장만 보고 사용 여부를 결정한다 |

**잘 쓰는 법 7가지**
1. **`description` 에 "무엇 + 언제".** ❌ `Lua 도우미` → ✅ `Lua 코드를 작성하거나 검토할 때 Lua 5.1 호환성을 점검한다.`
2. **스킬 하나에 역할 하나.** 겹쳐 쓸 수 있으니 합칠 필요가 없다.
3. **짧게.** 본문 1~2쪽. 긴 자료는 `resources/` 로.
4. **명령형.** "~한다", "~하지 않는다".
5. **"하지 말 것"과 "출력 형식"은 필수.** 결과가 일정해진다.
6. **예시 1개 이상.** 말보다 정확하다.
7. **시험한다.** 같은 프롬프트로 스킬 없이 / 적용해서 비교하고 로그에 남긴다.

**흔한 실수**

| 실수 | 결과 | 고치는 법 |
|---|---|---|
| `description` 이 막연함 | 안 불리거나 엉뚱할 때 불림 | 트리거 상황을 구체적으로 |
| 규칙 30개를 한 스킬에 | 일부가 무시됨 | 역할별로 쪼개기 |
| "알아서 잘" | 결과가 매번 다름 | 절차를 번호로 |
| 출력 형식 없음 | 긴 산문이 돌아옴 | 표나 목록 지정 |
| 과제를 통째로 대신하는 스킬 | 학습 효과 없음, 시연 때 설명 불가 | "골격과 힌트까지만" |

**설치**
- Gemini 앱: Customize → Skills → 업로드 (`SKILL.md`, 또는 최상위에 `SKILL.md` 가 있는 폴더/zip). Gemini 에게 "이 지시문으로 스킬 만들어 줘" 라고 해도 된다.
- Antigravity: `.agents/skills/<이름>/SKILL.md`. 전역은 `~/.gemini/config/skills/`.

### 2-3. 사용 예시

**예시 1 — 키트 스킬로 AI 코드 검토 (`lua51-guard`)**
```
lua51-guard 스킬로 아래 코드를 검토해 줘. 위반만 표로.
(방금 AI 가 만들어 준 enemy_states.lua 붙여넣기)
```
결과: `파일:줄 | 문제 | 수정안` 표 + `위반 N건`. 찾은 위반은 로그의 **거절·수정 사례**가 된다.

**예시 2 — 스킬 겹쳐 쓰기 (`game-ai-pattern-coach` + `mvc-boundary`)**
```
game-ai-pattern-coach 와 mvc-boundary 스킬을 함께 써서,
보스의 3단계 공격 패턴을 어떤 패턴으로, 어느 계층에 둘지 제안해 줘.
보스 체력이 66%, 33% 아래로 내려갈 때 공격 방식이 바뀐다.
```
결과: 패턴 비교표(State 추천 등) + 파일 배치(규칙은 `models/`, 연출은 `views/`) + 골격. 완성 코드는 주지 않는다.

**예시 3 — 내가 만든 스킬 (`wave-format`)**
```markdown
---
name: wave-format
description: 이 프로젝트의 웨이브 문자열("A3 B2 C1")을 만들거나 파싱하거나 검토할 때 사용한다.
---

# 형식
- 토큰은 공백으로 구분. 토큰 = 적 종류 대문자 1개 + 마리 수(1 이상 정수).
- 적 종류: A=돌진형, B=저격형, C=편대형. 그 외 문자는 오류.
- 웨이브는 models/waves.lua 의 배열에 문자열로 둔다.

# 하지 말 것
- 잘못된 토큰을 조용히 건너뛰지 않는다. error 로 알린다.
- 웨이브 데이터를 코드(if 문)로 하드코딩하지 않는다.

# 출력 형식
- 새 웨이브 제안 시: 문자열 + 한 줄 의도 (예: "B4 — 저격형만으로 압박")
```
효과: 웨이브 관련 요청마다 형식을 다시 설명하지 않아도 된다. **"같은 설명을 두 번 했다" → 스킬로 만든다**의 전형이다.

## 3. 워크플로 (Workflows) — Antigravity 전용

### 3-1. 개념

- **여러 단계를 늘 같은 순서로** 할 때 쓰는 체크리스트다. 채팅에 `/이름` 을 치면 AI 가 단계를 차례로 실행한다.
- 스킬은 AI 가 골라 쓰지만, 워크플로는 **내가 부를 때만** 실행된다.
- 워크플로 안에서 스킬과 에이전트, 다른 워크플로를 부를 수 있다.

### 3-2. 작성 가이드

```markdown
---
description: 한 줄 설명
---

# /이름

1. 첫 단계 (무엇을, 어떤 도구로)
2. 다음 단계
3. 실패하면 멈추고 알린다
```

- 파일당 12,000자 한도.
- 각 단계는 **확인 가능한 행동** 하나로 쓴다. "잘 정리한다" ❌ → "`git diff --stat` 결과를 보여 준다" ✅
- **멈추는 지점**을 넣는다: "승인을 기다린다", "실패가 있으면 멈춘다".
- 손으로 몇 번 해 본 과정을 "지금 한 과정을 워크플로로 만들어 줘" 라고 하면 초안이 나온다.

### 3-3. 사용 예시

**예시 1 — 세션 시작 (`/start-session`, 키트 제공)**
```
/start-session
지난 인계 메모: (붙여넣기)
```
진행: 목표 1개 확정 → 수정 허용 파일 확정 → 되돌리기 지점 커밋 → `planner` 계획 → **승인 대기**.

**예시 2 — 세션 마무리 (`/end-session`, 키트 제공)**
```
/end-session
```
진행: `test-runner` → diff 요약(**허용 범위 밖 변경 표시**) → `lua-reviewer` → `worklog-writer` 로그 초안 → 커밋 메시지 제안. 테스트 실패 시 멈춘다.

**예시 3 — 내가 만든 워크플로 (`/add-enemy-type`)**
```markdown
---
description: 새 적 종류를 MVC 순서대로 추가한다.
---

# /add-enemy-type

1. 사용자에게 적 이름, 행동(상태와 전이 조건), 웨이브 문자 기호를 묻는다.
2. headless-test-writer 스킬로 tests/<이름>_test.lua 를 먼저 만든다. 실패하는 것을 확인한다.
3. models/ 에 적 클래스를 추가한다 (class.lua 상속). 승인 후 진행.
4. 테스트를 실행한다. 실패하면 멈춘다.
5. views/EnemyView.lua 에 그리기를 추가한다 (주입받은 gfx 만).
6. tests/layer_check.lua 를 실행한다. 위반이 있으면 멈춘다.
7. wave-format 스킬 기준으로 웨이브 문자열 예시 1개를 제안한다.
```
효과: 적을 추가할 때마다 **테스트 → Model → View → 경계 검사** 순서를 지키게 된다.

## 4. 에이전트 (Agents) — Antigravity 전용

### 4-1. 개념

- 역할과 **쓸 수 있는 도구**가 정해진 AI 동료다. 메인 에이전트가 일을 맡기거나(서브에이전트), 내가 직접 골라 대화할 수 있다.
- 에이전트를 따로 만드는 가장 큰 이유는 **도구 제한**이다. 읽기만 가능한 리뷰어는 실수로라도 코드를 고칠 수 없다.
- 스킬은 "어떻게"를 알려 주고, 에이전트는 "누가, 어떤 권한으로"를 정한다.

### 4-2. 작성 가이드

```markdown
---
name: 이름
description: 메인 에이전트가 언제 이 에이전트에게 맡길지 판단하는 설명
tools: [view_file, grep_search]
mainAgent: true
subagent: true
---

# System Prompt
역할, 금지 사항

# 절차 / Guidelines

# 출력 형식
```

| 필드 | 설명 |
|---|---|
| `name` | 고유 이름 |
| `description` | **언제 맡길지**의 기준 |
| `tools` | 허용 도구. 예: `view_file`(읽기), `grep_search`(검색), `replace_file_content`(수정), `run_command`(명령 실행) |
| `mainAgent` | `true` 면 채팅에서 주 에이전트로 직접 선택 가능 |
| `subagent` | `true` 면 메인 에이전트가 불러서 맡길 수 있음 |

- `tools` 는 **필요한 최소한만**. 계획·리뷰는 읽기만, 실행 담당은 `run_command` 추가. 수정 담당은 기본 에이전트로 충분하다.
- frontmatter 아래 본문이 그 에이전트의 시스템 프롬프트다.
- 도구 이름은 버전에 따라 바뀔 수 있다. 공식 문서에서 확인한다.

### 4-3. 사용 예시

**예시 1 — 계획만 세우기 (`planner`, 키트 제공)**
```
planner 에이전트로: 저격형 적의 "예측 조준" Strategy 를 추가하는 계획을 세워 줘.
수정 허용 파일 후보와 먼저 쓸 테스트 목록까지.
```
결과: 목표, 수정 허용 파일, 단계별 계획, 테스트 목록, 위험 요소, 질문. **planner 는 파일을 고칠 수 없으므로** 승인 전에 코드가 바뀌는 일이 없다.

**예시 2 — 커밋 전 리뷰 (`lua-reviewer`, 키트 제공)**
```
lua-reviewer 에이전트로 지금 변경(git diff)을 리뷰해 줘.
```
결과: `심각도 | 파일:줄 | 문제 | 제안` 표 + `커밋 가능` / `수정 필요`. "높음"이 나오면 고친 뒤 다시 리뷰.

**예시 3 — 내가 만든 에이전트 (`report-helper`)**
```markdown
---
name: report-helper
description: 기말 보고서용 "Lua 문법 사용처 표"와 "패턴 적용 표"를 코드에서 찾아 초안을 만든다. 보고서 작성 시 사용한다.
tools: [view_file, grep_search]
mainAgent: true
subagent: false
---

# System Prompt
너는 읽기 전용 보고서 도우미다. 파일을 수정하지 않는다.
코드에 실제로 있는 것만 적는다. 없는 사용처를 지어내지 않는다.

# 절차
1. Lua 문법 사용처: setmetatable/__index, __add 등 메타메서드, 클로저, require 모듈,
   string.gmatch/format, pcall 을 grep 으로 찾는다.
2. 패턴 적용: State, Strategy, Observer(이벤트), Factory 흔적을 찾는다.
3. 각 항목에 파일:줄을 붙인다. "왜 썼는지" 칸은 비워 두고 학생이 쓰게 한다.

# 출력 형식
표 1: | 문법 | 파일:줄 | 코드 한 줄 |
표 2: | 패턴 | 파일:줄 | 역할 | 왜 썼는지(학생 작성) |
```
효과: 두 과목 보고서의 필수 표 초안을 빠르게 만든다. **"왜 썼는지"는 학생이 직접** 쓰므로 설명 능력은 그대로 평가된다.

## 5. 과제: 내 스킬(또는 워크플로·에이전트) 1개 만들기

**순서**
1. 작업 중 **같은 지시를 두 번 이상** 쓴 순간을 찾는다.
2. 위 구조로 파일을 만든다 (Gemini 앱만 쓰면 스킬).
3. 같은 프롬프트로 "없이" 와 "적용" 결과를 비교한다.
4. 작업 로그에 비교 결과와 파일 경로를 남긴다.

**아이디어:** `wave-format`(2-3 예시 3), `enemy-spec`(적 종류별 규칙), `my-naming`(이름 규칙), `/add-enemy-type`(3-3 예시 3), `report-helper`(4-3 예시 3)

**자가 점검**
- [ ] `description` 에 "무엇 + 언제" 가 있다
- [ ] 역할이 하나다
- [ ] "하지 말 것" 과 "출력 형식" 이 있다
- [ ] 예시가 1개 이상 있다
- [ ] 적용 전후 비교를 로그에 남겼다
