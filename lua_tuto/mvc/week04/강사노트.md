## 3. 꼭 전해야 할 정정 (2주차 숫자)
- 2주차 문서의 "변경 블록 23곳"은 **집계 오류**였고 실제는 **41곳**이다. 파일은 바뀌지 않았다(280→418줄, +176/−38 동일).
- 학생에게 그대로 말한다: "숫자는 사람이 세면 틀린다. **명령 출력으로 확인하라**" — `diff A B | grep -cE '^[0-9]'`. 이것 자체가 좋은 교훈이다.

## 4. 6절 실측 숫자 읽는 법 (질문이 많이 나오는 곳)
- "MVC 도 25곳이나 고쳤는데요?" → 숫자보다 **분포**를 본다. 2주차 41곳은 **한 파일 전체**에 흩어졌고 무관한 코드(일반 적 총알)까지 바뀌었다. 4주차 25곳은 **고칠 이유가 있는 파일**에만 있다. `EffectsView`·`PlayerModel`·`EnemyModel` 은 0줄.
- "코드가 더 길어졌는데요?" → 맞다(236 vs 176). README 의 "해결되지 않은 것"을 그대로 인정한다. MVC 는 **변경을 가두는** 기법이지 줄이는 기법이 아니다.
- "GameModel 에 12곳이 몰렸어요" → 정확한 관찰. 조율자(orchestrator)라서다. 5주차 State(보스전을 상태로 분리)·6주차 Store/이벤트로 다시 나눌 근거가 된다. **다음 주 동기 부여로 쓴다.**
- 3개 파일(conf, main, BulletModel)은 주석·창 제목만 바뀌었다는 점도 짚는다. **hunk 수는 "의미 있는 변경 수"와 다르다.**

## 5. 예상 질문
| 질문 | 답의 방향 |
|------|----------|
| "gfx 를 매번 넘기는 게 번거로워요. 그냥 love.graphics 쓰면 안 돼요?" | 써도 게임은 돈다. 다만 그 순간 View 테스트가 불가능해진다. 비용(인자 1개) vs 이득(테스트 9개) |
| "Controller 가 game 을 갖고 reset 하는데, 그럼 Controller 가 Model 을 바꾸는 거잖아요?" | 맞다, **그게 Controller 의 일**이다. 금지는 "규칙을 직접 구현하는 것"(basics 3절). `reset()` 이라는 Model 의 메서드를 **부르는** 건 괜찮다. |
| "EffectsView 에 상태가 있는데 View 가 상태를 가져도 되나요?" | **연출 상태**는 View 의 것이다. 금지는 **게임 상태**(점수·위치) 변경. 파티클이 사라져도 게임 결과는 같다. |
| "drainEvents 를 반복문 안에서 불러도 되지 않아요?" | 동작은 한다(이벤트를 스텝마다 넘길 뿐). 하지만 "이벤트는 프레임당 한 번 넘긴다"는 규칙이 하나 있는 편이 읽기 쉽다. 진짜 버그는 **안 부르는 것**(무한 누적). |
| "보스 총알이 적에게 막혀요. 버그인가요?" | 충돌 순서 규칙이다(적 판정이 먼저). `feature_test` 에 "편대가 보스 앞에 있으면 적이 먼저 맞는다" 테스트가 있다. **규칙을 테스트로 명문화**한 사례로 쓴다. 실제로 테스트 작성 중에 이 동작을 처음 발견했다. |

## 6. 개념 퀴즈 정답 & 채점 포인트 (README 10절)

**1. 주입 vs 직접 호출 (테스트 관점)**
- 직접 호출하면 테스트에서 `love` 가 없어 실행조차 안 된다. 주입하면 가짜 gfx 를 넣어 **무엇을 그리려 했는지** 기록·검사할 수 있다.

**2. read 1회가 보장하는 것 / 못 하는 것**
- 보장: 입력이 **일정하면** 프레임률과 무관하게 같은 결과. 한 프레임의 모든 스텝이 같은 스냅샷을 쓴다.
- 못 하는 것: 입력이 **바뀌는 순간**은 프레임 경계로 반올림된다. 그래서 60fps 와 20fps 의 결과가 다를 수 있다(0.31초에 키를 떼면 381.3 vs 392.0).
- 해결? 실시간 입력의 반올림은 LÖVE 에서 없앨 수 없다(키 이벤트에 정밀 시각이 없음). 6주차 스텝별 입력 기록은 **일어난 판을 어느 프레임률로든 똑같이 재현**할 뿐이다. (초판은 "6주차가 해결"이라고 적었는데, 6주차를 만들며 바로잡았다.)
- ❌ 감점: "read 를 프레임당 1회 하면 프레임률과 무관하게 항상 같다". 초판 강사노트에도 있었던 오류다. 학생에게 그대로 말해 줘도 좋다.
- 참고: 반복문 안에서 `read` 를 여러 번 불러도 결과는 같다. `love.keyboard` 상태는 프레임 안에서 바뀌지 않기 때문이다. 1회로 하는 이유는 정확성보다 **의도를 분명히** 하기 위해서다.

**3. 연출 난수 vs 규칙 난수**
- 파티클 방향은 **게임 결과에 영향이 없다** → 비결정이어도 테스트·리플레이가 깨지지 않는다.
- 적 발사 대상은 **게임 결과를 바꾼다** → 주입 RNG 로 결정적이어야 한다.
- ❌ 감점: "View 에서 난수를 쓰면 안 된다"

**4. 금지 테스트의 짝**
- "적 수만큼 그린다", "HUD 가 점수를 출력한다" 같은 **기능 테스트**. 금지 테스트만 있으면 아무것도 안 하는 코드가 만점을 받는다.

**5. MVC 가 해결 못 한 것**
- ① 총 코드량 증가 ② `GameModel` 로 변경 집중 → 5주차(State 패턴으로 보스전·씬 분리), 6주차(이벤트/Store).

## 7. 자주 막히는 곳
- **`setRequirePath` 를 `love.load` 안에 넣음**: 파일 맨 위 `require` 가 먼저 실행되어 모듈을 못 찾는다. **파일 최상단**에 둔다.
- **`GameView:draw` 에서 `pop` 을 HUD 뒤에 둠**: HUD 가 흔들린다. `push/pop` 짝은 테스트가 잡지만 순서는 눈으로 확인.
- **`InputController:read` 가 매번 새 테이블 반환**: 동작은 하지만 1주차 GC 원칙 위반. 재사용 테이블 이유를 짚는다.
- **`keypressed` 에서 `love.event.quit()` 직접 호출**: `layer_check` 가 잡는다. 초판에서는 잡지 못했다. 당시 규칙이 `love.graphics`/`love.audio` 만 금지했기 때문이고, 검토를 하면서 "View·Controller 는 `love` 전체 금지"로 고쳤다. "금지 목록(블랙리스트)은 빈틈이 생기기 쉽다"는 사례로 쓸 수 있다.
