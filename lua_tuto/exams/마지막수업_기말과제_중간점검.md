1. `README.md`의 명령만 보고 테스트를 실행합니다.
2. 실패한 테스트가 있으면 구현보다 **테스트 조건과 실제 입력**을 먼저 확인합니다.

5. 같은 시드와 입력으로 AI를 여러 번 갱신해 결과가 같은지 비교합니다.
6. 마지막 커밋을 `docs/git_log.txt`와 연결되는지 확인합니다.

### 권장 검증 명령

학생 환경에 따라 `luajit` 또는 `lua5.1`을 사용합니다. 고정된 설치 경로는 가정하지 않습니다.

```bash
cd project/tests
luajit run_all.lua src
luajit layer_check.lua src
```

통과 결과는 작업 로그에 **명령과 출력 요약**을 함께 남깁니다.

## 3. 잘못된 진행을 빠르게 구분하는 기준

### 파서

아래처럼 “맞는 일부만 찾는” 구현은 잘못된 입력을 통과시킬 수 있습니다.

```lua
line:gmatch("(%a+)%s+([%d%.]+)")
```

한 줄을 먼저 토큰 전체로 나누고, 토큰 개수와 전체 형식을 검사한 뒤 변환합니다.
`"at abc grunt"`와 `"at 1 grunt 100 200 extra"`가 조용히 무시되면 안 됩니다.

### 난수

적 AI에서 `math.random`을 직접 호출하면 같은 입력을 테스트할 수 없습니다.
Model에 난수를 만들고, 상태 업데이트에는 주입된 `game.rng`만 전달합니다.

### 씬과 모델

- 씬은 화면 흐름과 입력 전달을 담당합니다.
- 적 AI 상태는 Model 안에서 전이합니다.
- 씬에서 적 상태를 직접 변경하지 않습니다.
- 저장 파일 입출력은 `main.lua`에 두고, 저장 Model은 문자열 변환과 검증만 담당합니다.

### AI 작업 기록

“코드를 만들어줘”만으로는 부족합니다. 최소한 다음 중 하나의 실제 실패·수정 사례가 있어야 합니다.

- Lua 5.3 문법 또는 전역 변수 사용을 발견해 수정한 사례
- `layer_check` 경계 위반을 거절하고 다시 지시한 사례
- 명세·계약·테스트를 첨부한 프롬프트와 일반 프롬프트의 차이

## 7. 바이브 코딩을 취업에 도움이 되는 연습으로 바꾸는 법

좋은 바이브 코딩은 **AI에게 빠르게 많이 만드는 것**이 아니라,
AI가 만든 결과를 사람이 **정의하고·검토하고·검증하고·설명하는 것**입니다.

### 7-1. 에이전트는 역할별로 작게 쓴다

한 에이전트에게 게임 전체를 맡기면 기능은 빨리 생겨도 구조와 원인을 설명하기 어렵습니다.
작업별 담당을 나누는 편이 좋습니다.

| 역할 | 맡길 일 | 사람이 마지막에 확인할 것 |
|---|---|---|
| 플래너 | 요구사항을 작은 태스크로 분해 | 범위, 선후 관계, 완료 기준 |
| 구현 에이전트 | 허용한 파일에서 기능 구현 | 실제 diff, 불필요한 파일 변경 |
| 테스트 에이전트 | 재현·경계·오류 테스트 작성 | 테스트가 실제 버그를 잡는가 |
| 리뷰 에이전트 | 계층 위반, 가짜 통과, 복잡도 검토 | 지적이 사실인지, 우선순위는 맞는지 |
| 문서·로그 에이전트 | 작업 기록과 보고서 초안 | 줄 번호, 커밋, 실패 기록의 사실성 |

핵심은 **한 세션에서 한 목표와 한 커밋 정도만** 다루는 것입니다.
세션이 길어지면 처음의 제약을 잊기 쉬우므로, 끝날 때 다음 세션용 인계 메모를 남깁니다.

### 7-2. 스킬은 “자주 반복하는 판단”을 고정한다

스킬은 답안 생성기가 아니라, 여러 번 반복할 검사를 재사용 가능한 규칙으로 만든 것입니다.

```text
입력: 어떤 작업에서 스킬을 쓰는가
절차: 어떤 순서로 확인하는가
금지: 절대 하면 안 되는 것은 무엇인가
판정: 언제 통과 또는 실패로 보나
출력: 어떤 형태로 결과를 보고하나
```

추천 연습:

1. 첫 구현에서는 규칙 없이 AI 결과를 받고 문제를 기록합니다.
2. 반복된 문제를 스킬 또는 규칙 파일로 만듭니다.
3. 같은 작업을 다시 시켜 적용 전후를 비교합니다.
4. “더 짧아졌다”가 아니라 **오류 수, 번짐 범위, 테스트 실패 재현성**으로 비교합니다.

예를 들어 `lua51-guard`는 Lua 5.1 금지 문법과 전역 누수를,
`mvc-boundary`는 계층 책임 위반을 검사합니다.

### 7-3. 패턴은 이름이 아니라 제거하는 증상으로 배운다

디자인 패턴은 외워서 넣는 것이 아니라, 현재 문제를 가장 작게 해결하는 선택입니다.

| 문제 증상 | 먼저 볼 패턴 | 선택하지 않을 때의 조건 |
|---|---|---|
| 시간이 지나며 행동이 바뀜 | State | 경우가 2~3개뿐이고 전이가 단순함 |
| 종류 문자열로 제품 생성 | Factory | 생성 지점이 하나이고 종류가 늘지 않음 |
| 처리기는 모르고 결과만 알림 | Observer / 이벤트 큐 | 직접 호출이 더 명확하고 구독자가 하나임 |
| 알고리즘만 교체 | Strategy | 알고리즘 교체 없이 데이터 몇 개만 다름 |
| 기존 객체에 기능 덧붙임 | Decorator | 조합 순서가 중요하지 않고 간단한 분기로 충분함 |

면접에서 좋은 설명은 정의 암기가 아니라 다음 순서입니다.

```text
원래 어떤 증상이 있었는가
어떤 대안을 비교했는가
왜 이 패턴을 골랐는가
이 선택의 단점은 무엇인가
그 단점은 어떻게 검증했는가
```

### 7-4. 아키텍처는 “변경이 퍼지는 범위”로 평가한다

“MVC다”라고 쓰는 것보다 새 기능을 추가했을 때 어떤 파일과 계층이 바뀌는지가 더 중요합니다.
R7 번짐 측정은 이 질문을 숫자로 답하게 합니다.

- 새 입력 방식 → Controller만 바뀌는가?
- 새 화면 연출 → View만 바뀌는가?
- 새 적 규칙 → Model과 등록 지점에만 바뀌는가?
- 새 화면 흐름 → Scene과 조립 코드에만 바뀌는가?
- 이유 없이 여러 계층이 함께 바뀌면 책임이나 의존 방향을 다시 확인한다.

### 7-5. AI 결과는 4단계로 검토한다

1. **이해**: 각 함수와 의존성을 한 줄씩 설명할 수 있는가?
2. **경계**: 수정 금지 파일이나 계층 규칙을 어기지 않았는가?
3. **반례**: 빈 값, 잘못된 형식, 누락, 중복, 경계값에서 어떻게 되는가?
4. **증거**: 테스트·정적 검사·작은 실행 결과 중 어떤 것이 주장을 뒷받침하는가?

“테스트가 통과했다”만 쓰지 않고, 버그가 다시 생기면 같은 테스트가 실패하는지도 확인합니다.

### 7-6. 포트폴리오로 남길 5가지 증거

취업 준비에서 유용한 것은 화려한 결과 화면 하나보다 다음 다섯 가지입니다.

1. 문제와 완료 기준이 적힌 짧은 이슈 또는 README
2. 설계 대안과 패턴 선택 이유
3. AI에게 준 프롬프트와 결과를 거절·수정한 기록
4. 실패 테스트 → 원인 분석 → 수정 → 회귀 테스트 과정
5. 변경 전후 번짐·성능·복잡도 같은 측정값

아래 문장은 면접에서 그대로 설명할 수 있어야 합니다.

> “AI가 처음 만든 코드는 동작했지만 경계를 어겼습니다. 저는 이를 어떤 증거로 발견했고,
> 어떤 제약을 프롬프트에 추가했으며, 같은 기능을 더 좁은 변경으로 검증했습니다.”

반대로 “AI가 만들어 줬습니다”보다 중요한 것은
**어디까지 AI가 했고, 어디에서 내가 판단했으며, 왜 그 결정을 믿을 수 있는가**입니다.

### 7-7. 90분 연습 예시

마지막 수업 또는 자기 학습에서 다음 순서로 진행할 수 있습니다.

| 시간 | 활동 | 산출물 |
|---|---|---|
| 15분 | 기능 하나의 증상과 완료 기준 작성 | 짧은 태스크 정의 |
| 15분 | 패턴 또는 구조 대안 2개 비교 | 선택 이유와 단점 |
| 20분 | 테스트 1개와 실패 재현 | AI 작업 전 증거 |
| 25분 | 에이전트 또는 스킬로 최소 구현 | 제한된 파일의 diff |
| 10분 | 리뷰·계층·경계값 검사 | 검증 결과 |
| 5분 | 프롬프트, 거절, 다음 개선점 기록 | 포트폴리오용 로그 |

## 8. 모범 답안을 볼 때

[모범 답안 안내](기말과제_모범답안/README.md)는 복붙 대상이 아니라
채점자가 찾는 증빙의 형태를 확인하는 용도입니다. 특히 다음을 비교합니다.

1. 요구사항과 테스트가 서로 대응하는가?
2. 보고서의 줄 번호가 실제 최종 코드와 일치하는가?
