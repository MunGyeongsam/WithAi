# 퀴즈: 언제 어떤 패턴을 쓰는가 (Design Pattern Selection Quiz)

> 대상: `lua_tuto/design_patterns`의 22개 패턴
> 목표: 패턴 암기가 아니라 **상황 신호 → 패턴 선택** 판단력을 점검한다.
> 정답과 해설은 [퀴즈_언제어떤패턴_정답.md](퀴즈_언제어떤패턴_정답.md)에 있다.

- 생성(5): abstract_factory, builder, factory_method, prototype, singleton
- 구조(7): adapter, bridge, composite, decorator, facade, flyweight, proxy
- 행동(10): chain_of_responsibility, command, iterator, mediator, memento, observer, state, strategy, template_method, visitor

## Part A — 상황 → 패턴 고르기 (객관식, 각 4점 · 10문항)

각 상황에서 가장 알맞은 패턴 하나를 고른다.

**A1.** 적 AI의 공격 방식이 `if difficulty == ...` 분기로 흩어져 있다. 런타임에 난이도별 공격 로직을 통째로 바꿔 끼우고 싶다.
- (a) observer  (b) strategy  (c) adapter  (d) singleton

**A2.** 플레이어 점수가 바뀌면 UI 갱신, 효과음 재생, 업적 체크가 동시에 일어나야 한다. 점수 코드는 누가 반응하는지 몰라야 한다.
- (a) observer  (b) command  (c) facade  (d) state

**A3.** 캐릭터가 `idle → run → jump → fall`처럼 현재 모드에 따라 같은 입력에도 다르게 동작한다. 거대한 조건 분기를 없애고 싶다.
- (a) strategy  (b) state  (c) visitor  (d) proxy

**A4.** 입력 키 리바인딩, 되돌리기(undo), 매크로 녹화가 필요하다. 요청을 즉시 실행만 하지 말고 값으로 보관하고 싶다.
- (a) memento  (b) iterator  (c) command  (d) bridge

**A5.** 외부 결제 SDK의 함수명·인자가 우리 코드가 기대하는 계약과 다르다. 기존 코드를 고치지 않고 끼워 맞추고 싶다.
- (a) facade  (b) adapter  (c) decorator  (d) factory_method

**A6.** 오디오·세이브·에셋 로딩의 초기화와 호출 순서가 복잡하다. 상위 코드에는 단순한 창구 하나만 노출하고 싶다.
- (a) facade  (b) mediator  (c) composite  (d) proxy

**A7.** 타일맵에 같은 종류의 타일 수천 개가 있다. 공유되는 정의(스프라이트·크기)를 중복 저장해 메모리가 터진다.
- (a) prototype  (b) flyweight  (c) builder  (d) singleton

**A8.** UI 트리(패널 안에 패널, 그 안에 버튼)를 `draw()` 한 번으로 재귀 처리하고 싶다. 잎과 그룹을 같은 방식으로 다루고 싶다.
- (a) composite  (b) chain_of_responsibility  (c) template_method  (d) iterator

**A9.** 세이브/체크포인트/되돌리기를 위해 객체 상태를 스냅샷으로 저장·복원하되, 내부 구조는 밖으로 노출하고 싶지 않다.
- (a) command  (b) memento  (c) prototype  (d) observer

**A10.** 무거운 리소스(대용량 텍스처)를 실제로 쓸 때까지 로딩을 미루고, 접근 권한도 함께 통제하고 싶다. 사용 계약은 그대로 유지한다.
- (a) decorator  (b) proxy  (c) adapter  (d) facade

## Part B — 비슷한 패턴 구분하기 (단답/서술, 각 6점 · 5문항)

헷갈리기 쉬운 짝의 **선택 기준 차이**를 한두 문장으로 쓴다.

**B1.** `strategy` vs `state` — 둘 다 "행동을 객체로 교체"한다. 언제 state를 고르는가?

**B2.** `adapter` vs `facade` — 둘 다 "감싸는" 패턴이다. 결정적 차이는 무엇인가?

**B3.** `decorator` vs `proxy` — 둘 다 같은 계약으로 원본을 감싼다. 목적이 어떻게 다른가?

**B4.** `factory_method` vs `abstract_factory` — 생성 책임을 분리하는 두 패턴의 적용 신호 차이는?

**B5.** `command` vs `memento` — 되돌리기(undo)를 둘 다 돕는다. 각자 무엇을 값으로 캡슐화하는가?

## Part C — 신호를 패턴에 연결하기 (연결, 각 2점 · 7문항)

왼쪽의 "코드 냄새/요구"를 오른쪽 패턴에 연결한다.

| # | 신호 | | 패턴 |
| --- | --- | --- | --- |
| C1 | 변하는 축이 둘 이상이라 기능×구현 조합이 폭발한다 | | ⓐ chain_of_responsibility |
| C2 | 입력·이벤트를 여러 단계로 거르며 "처리 못 하면 다음에 위임" | | ⓑ bridge |
| C3 | 비슷한 절차가 몇 단계만 다르고 큰 흐름은 같다 | | ⓒ mediator |
| C4 | 참가자들이 서로 직접 참조해 그물처럼 얽힌다 | | ⓓ iterator |
| C5 | 컬렉션 내부 구조를 숨긴 채 원소를 하나씩 넘기고 싶다 | | ⓔ template_method |
| C6 | 구조는 안정적이고 연산(순회 작업)만 자주 추가된다 | | ⓕ builder |
| C7 | 생성자 인자가 너무 많고 선택 필드가 뒤섞인다 | | ⓖ visitor |

## Part D — 과적용 경계 (서술, 10점 · 2문항)

Lua/LÖVE2D에서 "패턴을 굳이 쓰지 않는 게 나은" 경우를 설명한다.

**D1.** `singleton`을 Lua에서 과용하지 말아야 하는 이유를, `require` 동작과 연결해 설명하라.

**D2.** 타입과 연산이 몇 개 안 될 때 `visitor` 대신 더 단순한 Lua식 대안은 무엇이며 왜 더 나은가?
